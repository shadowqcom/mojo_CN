本页面提供了 Mojo 编程语言预期如何通过一系列阶段演进的高层路线图。本路线图提供**方向性指导**（而非工程计划），并且**可能会发生变化**。随着我们构建、学习和扩展 Mojo 的用例，我们将迭代、调整和投资以解除优先级的阻碍。

我们还会定期在 [Modular 论坛公告区](https://forum.modular.com/c/modular/announcements/9)分享路线图更新。

:::note[阶段]

以下阶段是概念性的工作分组——而非版本号——并且没有完成时间表。我们尚未建立长期版本方案、最终确定语言演进的方法，或决定"稳定性"将意味着什么以及何时实现。

:::

## Mojo 的北极星

正如 [Mojo 愿景](/docs/vision/)中所述，我们创建 Mojo 是为了用一种语言统一开发者，该语言为加速器硬件提供符合人体工程学的编程功能，并能够扩展到解决 AI 和系统编程中的其他挑战。

我们的目标雄心勃勃，我们正在应对许多语言和系统数十年来一直挣扎的挑战。我们相信 Mojo 拥有**技术、设计原则和社区优先理念**的正确组合来取得成功，但这只有在我们保持专注并做出与长期愿景一致的审慎权衡时才能实现。

风险很高——成功的编程语言塑造整个生态系统，支持数百万开发者，并定义软件的构建方式。这意味着我们必须**抵制追逐短期胜利的冲动**，不能以牺牲长期的清晰度、一致性和质量为代价。

我们的方法是保持短期开发的专注和以可衡量的成果为锚点，同时为通用性构建，使 Mojo 最终成为一种跨越 CPU、GPU 和其他硬件的通用语言，加上 Python 所用于的无数应用。

我们知道这条路不会完美，我们会犯错误。但凭借坚实的基础和积极参与的、深思熟虑的社区，我们可以**一起学习、迭代和改进**。

## 阶段 0：初始搭建

:::tip[✅ 已完成]

阶段 0 已完成。

:::

阶段 0 专注于基础性语言工作：实现核心解析器、定义内存类型、函数、结构体、初始化器、参数约定等。

随着开发加速，出现了多个库来满足即时需求，功能上经常重叠（例如，多种指针类型）。随着语言稳定下来，我们将这些库整合为一个连贯且一致的基础。

## 阶段 1：高性能 CPU + GPU 编程

:::caution[🚧 进行中]

阶段 1 正在进行中。

:::

阶段 1 将 Mojo 从"原型内核 DSL"转变为现实世界加速计算工作负载的可行基础。本阶段专注于使 Mojo 成为一种强大而富有表现力的语言，用于在 CPU、GPU 和 ASIC 上编写高性能内核。我们还希望解锁 CPU 的其他性能用例，特别是以无缝方式扩展 Python 包的能力。

但仅有性能是不够的。我们同样关注：

- **表达力**，用于构建健壮的库
- **良好的错误消息**，用于提升开发者生产力
- **快速的编译时间**，以支持迭代速度

阶段 1 的结束是**开源 Mojo 编译器**的自然节点。

### 泛型和元编程功能

阶段 1 的骨干是 Mojo 的**元编程系统**，结合了**现代泛型类型系统**，可在代码实例化之前在编译时捕获错误。以下功能捕捉了我们认为 Mojo 应该如何演进的方向，但可能会随着我们的成长而变化：

- ✅ **编译时构造**：参数系统、编译时解释器、`if` 和 `for` 循环等。

- ✅ **Trait 联合**：允许 `Copyable & Defaultable` 交集以实现精确的 trait 一致性。参见 [trait 组合提案](https://github.com/modular/modular/blob/main/mojo/proposals/trait_composition.md)。

- ✅ **可预测的依赖类型**：支持高级参数化算法，同时避免重绑定。

- ✅ **参数化编译时值**：计算参数化值，超越类型和函数。参见[参数化别名提案](https://github.com/modular/modular/blob/main/mojo/proposals/parametric_alias.md)。

- ✅ **默认 trait 方法**：启用静态组合（mixin 风格）。

- ✅ **参数化 raises**：能够抛出 `Error` 以外的类型，因此支持像 `map` 这样传播其闭包参数"可抛出性"的高阶函数。

- 🚧 **闭包精化**：改进捕获建模并统一编译时/运行时表示。

- ✅ **`where` 子句**：启用早期约束检查和更好的泛型错误消息。参见 [where 子句提案](https://github.com/modular/modular/blob/main/mojo/proposals/where_clauses.md)。

- ✅ **条件一致性**：允许基于参数谓词的 trait 一致性。

- 🚧 **结构体扩展**：事后类型扩展和更好的模块化重构。参见[结构体扩展提案](https://github.com/modular/modular/blob/main/mojo/proposals/struct-extensions.md)。

- 🚧 **线性类型**：支持所有权模式；受条件一致性阻塞。

- 🚧 **稳定化标记**：用于标记标准库 API 成熟度级别的机制。

### Python 互操作性

我们希望 Mojo 成为扩展和加速现有 Python 代码的平易近人的方式。我们希望将"nanobind"等流行库的关键功能作为指导：

- ✅ **构建集成**：Mojo 构建系统与 Python 打包之间的无缝连接。

- ✅ **Python 导出**：支持将函数和初始化器暴露给 Python。

### 核心语言可用性和人体工程学

Mojo 应该对核心的 Python 类任务"开箱即用"，同时提供系统程序员期望的控制力：

- ✅ **基本构造**：函数、结构体、控制流（`if`、`for` 等）。

- ✅ **字面量支持**：无限精度 `int`/`float`、集合、推导式。

- 🚧 **集合**：完善核心类型如 `List`、`Dict`、`Iterator`、`SIMD`、`String` 等，以利用阶段 1 的语言功能集。例如，参见[使 SIMD 可比较](https://github.com/modular/modular/blob/main/mojo/proposals/simd-comparable.md)和[字符串类型提案](https://github.com/modular/modular/blob/main/mojo/proposals/string-design.md)。

- ✅ **不安全编程**：精化 `UnsafePointer` 和低级原语。

- 🚧 **可变参数**：完整支持 `*args`、`**kwargs`。

- ⬜ **Lambda 语法**，用于内联闭包声明。

- ⬜ **稳定且健壮的工具链**：交叉编译、打包和构建系统、标准库中的测试和基准测试框架、调试器、性能分析器等。我们预计会在这方面取得重大进展，但不会在阶段 1 完全完成所有有趣的工作。

  - 🚧 Mojo 语言服务器协议支持和 VSCode 扩展
  - 🚧 测试框架
  - ⬜ 基准测试框架
  - 🚧 调试器
  - ⬜ 性能分析器
  - ⬜ 打包和构建系统

- 🚧 **GPU 可编程性抽象**：丰富且易于使用的张量类型、数据布局和基本算法抽象。

### 语法和表面语言打磨

这些看起来可能很小，但它们显著影响开发者人体工程学并减少未来的源代码不兼容性：

- ✅ **参数约定**：精化 `init`/`del` 行为、命名和默认约定。

- ✅ **字面量精化**：使用依赖类型提高无限精度字面量的可靠性。参见[集合字面量设计](https://github.com/modular/modular/blob/main/mojo/proposals/collection-literal-design.md)和[修复简单字面量提案](https://github.com/modular/modular/blob/main/mojo/proposals/fixing-simple-literals.md)。

- 🚧 **属性宏**：使用 trait 和其他现有语言功能（缩小语言）替换 `@__nonmaterializable`、`@value` 等临时构造。例如，参见[升级"trivial"提案](https://github.com/modular/modular/blob/main/mojo/proposals/upgrading-trivial.md)和[升级 `@value` 装饰器](https://github.com/modular/modular/blob/main/mojo/proposals/upgrading-value-decorator.md)。

### 非目标

我们在阶段 1 中有意_不_追求以下内容：

- **语法糖**：我们将大部分语法糖推迟到核心语言稳定且可组合之后。

- **无类型的 Python 风格代码**：目前需要显式的 `PythonObject` 类型注解。

- **Python 库对等性**：我们预计阶段 1 会有许多缺失的 API（例如可能是文件系统 API）。

## 阶段 2：系统应用编程

:::danger[⏰ 尚未开始]

阶段 2 尚未开始。

:::

一旦核心泛型类型系统和系统编程功能趋同并稳定下来，我们将开始扩展 Mojo 以支持应用级编程——即通常由 Rust 和 C++ 等语言解决的问题类型。

话虽如此，**我们的目标不是与 Rust 或 C++ 逐个功能对标**。我们的目标是让 Mojo 保持相对小巧和可教学——一种[没有不必要复杂性](/docs/vision#managing-language-complexity)地解决特定问题的语言。

:::note

以下功能目前都没有确定范围，我们对关于它们的设计讨论不感兴趣。我们在此列出它们是为了理解阶段 1 的非目标，并合理化事物如何随时间积累。我们的重点仍然坚定地放在完成阶段 1 上，然后才会在此投入大量精力。

:::

### 语言和抽象功能

- **一等 `async` 支持**：与 Mojo 的类型和内存模型完全集成。

- **存在类型 / 动态 trait**：用于构建灵活的运行时抽象。

- **更丰富的元类型**：扩展对类型级编程的支持。

- **代数数据类型与模式匹配**：实现富有表现力的状态建模。

- **动态反射功能。**

- **初始分布式编程支持。**

### 内存安全模型：快速、富有表现力、渐进式

Mojo 代码默认应该是内存安全的，同时仍然快速、富有表现力，并且对初学者来说逐渐增加复杂性。虽然阶段 1 为[内存安全](/docs/manual/values/)提供了强大的框架，但仍然存在默认情况下安全无法保证的情况，我们预计这些问题要到阶段 2 才能完全解决。

- **快速**：Mojo 应该使程序员能够默认编写高性能的内存安全代码，同时继续为专家使用提供不安全原语。

- **富有表现力**：Mojo 的来源（origin）系统应该启用更多的可变别名，以提供比 Rust 等语言更具表现力的编程模型。这是可取的，因为可变别名的可变对象在 Python 和 C++ 社区中广泛存在，通常是出于表达力、简单性和/或性能的正当理由。

- **渐进式**：我们希望渐进式地披露复杂性——应该容易上手并立即在 Mojo 中高效工作，用户可以根据需要逐步学习更高级的功能。

这可能需要：

- 确定间接来源（indirect origins）。

- 支持结构体字段的可变别名。

- 支持函数参数的可变别名。

- 防止解引用任何指向已释放引用计数对象字段的引用。

- 访问控制功能，例如 `private` 修饰符（或形式化下划线约定）以防止违反抽象边界。

- 消除未定义行为，特别是在核心类型和内置操作中。

这将使我们更接近使 Mojo 的内存安全模型快速、富有表现力并对初学者渐进式增加复杂性的目标——使 Mojo 对 Python 和 C++ 开发者更易接近。

### 其他应用级编程功能

我们可能会探索卫生的、可导入的宏，以受控方式扩展 Mojo 的表面语法。例如，启用像 `parallel_for` 这样的构造，感觉像内置的 `for` 循环一样无缝，但在库中定义。

我们还可能探索使 Mojo 优化器可通过"库定义"的优化进行扩展。例如，允许 Mojo 库作者定义重写规则，将 `String.__add__(x, String.__add__(y, z))` 转换为 `String.concat(x, y, z)`。其确切形式和最终能力将在以后定义。

## 阶段 3：动态面向对象编程

:::danger[⏰ 尚未开始]

阶段 3 尚未开始。

:::

最终，我们希望 Mojo 支持使 Python 出色的核心动态功能，包括对无类型变量、类、继承等的支持。我们对这些功能将如何与其他功能组合有一些想法，但将详细的规划和范围界定推迟到早期阶段完成之后。

随着 Mojo 在阶段 3 中成熟，我们相信 Mojo 将越来越兼容 Python 代码，并让 Python 用户深感熟悉，只是更高效、更强大、更一致、更安全。Mojo 可能会也可能不会演变成 Python 的完整超集，如果不是也没关系。

我们受到鼓舞的是，AI 辅助编码工具已经在帮助将 Python 迁移到 Mojo 方面做得很好，我们相信未来的工具和生态系统成熟度将使这种演变更加顺畅。

## 持续投入

以下主题将在 Mojo 的整个生命周期中持续进行，不与任何特定阶段挂钩：

- **错误消息和诊断**：总有改进空间，但参数推断和详细器错误特别需要改进。

- **编译时间**：我们将继续推动更快的开发者迭代周期。

- **标准库清理**：API 整合、规范化和新功能。

- **硬件支持**：扩展 Mojo 后端以支持新架构。

## 为 Mojo 贡献

我们致力于将 Mojo 全部开源，但该语言仍然非常年轻，我们相信一个拥有共同愿景的紧密工程师团队比社区驱动的努力行动更快。因此，我们将继续在 Modular 内规划和优先排序 Mojo 路线图，直到其更多内部架构被完善。

然而，Mojo 标准库已经开源，我们很乐意接受你的贡献。虽然本路线图提到了一些标准库类型，因为它们依赖于 Mojo 编译器的更改，但标准库的大量工作在此并未涵盖。

你可以从以下贡献者文档中了解更多关于为标准库贡献的信息：

- [贡献者指南](https://github.com/modular/modular/blob/main/mojo/CONTRIBUTING.md)

如果你在使用 Mojo 时遇到任何错误，请在 [GitHub 上提交 issue](https://github.com/modular/modular/issues)。
