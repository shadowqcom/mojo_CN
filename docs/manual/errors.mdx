Mojo 将错误表示为值——具体来说，是函数的替代返回值。与 C++ 或 Java 等语言中的栈展开异常不同，Mojo 错误不需要昂贵的调用栈展开，因此其运行时开销与返回和检查一个额外的 `Bool` 一样低。这种设计还使得在传统异常不可用的上下文（如 GPU 内核）中能够进行错误处理。

本页面涵盖以下内容：

- [**引发错误**](#raise-an-error) — 使用内置的 `Error` 类型来引发带有字符串消息的错误。
- [**处理错误**](#handle-an-error) — 使用 `try`/`except`/`else`/`finally` 来检测和恢复错误。
- [**类型化错误**](#typed-errors) — 将自定义错误类型定义为结构体，用于结构化错误数据和编译时类型检查。
- [**表示多种错误条件**](#representing-multiple-error-conditions) — 使用枚举错误类型或 `Variant` 类型进行模式匹配。
- [**`Never` 类型**](#the-never-type) — 标记总是引发或从不引发错误。
- [**参数化引发**](#parametric-raises) — 编写将错误类型从参数传播到调用者的泛型函数。
- [**类型化错误和 `Error` 交互**](#typed-errors-and-error-interaction) — 处理同时使用两种错误风格的代码。
- [**堆栈跟踪**](#enable-stack-trace-generation-for-errors) — 启用堆栈跟踪收集以进行调试。
- [**上下文管理器**](#use-a-context-manager) — 使用 `with` 语句安全地管理资源。

错误会中断程序的正常执行流程。如果您在当前函数中提供了错误处理器（使用 [`try`/`except`](#handle-an-error)），执行将恢复到该处理器。如果错误未在当前函数中处理，它会传播到调用函数，依此类推。如果错误未被任何处理器捕获，您的程序将以非零退出代码终止并打印错误消息：

```output
Unhandled exception caught during execution: record not found
```

## 引发错误

内置的 [`Error`](/docs/std/builtin/error/Error/) 类型是大多数 Mojo 代码的默认错误类型。它携带一个描述发生了什么问题的文本消息，是应用级错误处理的正确选择——简单、广泛支持，并且足以满足大多数用例。

您可以使用构造函数或字符串字面量简写来引发 `Error`：

```mojo
# 这些是等价的
raise Error("file not found")
raise "file not found"
```

字符串字面量形式是一种便利——编译器会自动将其包装在 `Error` 中。

通过声明 `raises`，您告诉 Mojo 一个函数可能会引发错误：

```mojo
def read_file_fn(path: String) raises -> String:
    if not path:
        raise "path cannot be empty"
    return "contents of " + path
```

:::tip

如果您需要结构化错误数据——如错误代码和描述的独立字段——或者需要 GPU 内核的零分配错误，请参阅本页面后面的 [类型化错误](#typed-errors)。对于大多数应用代码，带有描述性字符串消息的 `Error` 就足够了。

:::

## 处理错误

Mojo 使用 `try`/`except` 来检测和处理错误。完整语法如下：

```mojo
try:
    # 可能引发错误的代码
except e:
    # 如果发生错误则运行
else:
    # 如果没有错误则运行
finally:
    # 无论结果如何都运行
```

您必须包含 `except` 和 `finally` 中的一个或两个。`else` 子句是可选的。

### 每个子句的工作原理

- `try` — 包含可能引发错误的代码。如果没有错误发生，整个代码块执行。如果发生错误，执行在 `raise` 点停止，然后继续执行 `except` 子句（如果存在）或 `finally` 子句。

- `except` — 仅在 `try` 代码块中发生错误时运行。如果您提供了一个变量名（`except e:`），错误将绑定到该变量。`try` 代码块只能有一个 `except` 子句。

- `else` — 仅在 `try` 代码块中没有发生错误时运行。如果 `try` 子句通过 `continue`、`break` 或 `return` 退出，`else` 子句将被*跳过*。

- `finally` — 在 `try` 和任何 `except` 或 `else` 子句之后运行，无论结果如何。即使另一个子句通过 `continue`、`break`、`return` 退出或引发新错误，它也会执行。使用 `finally` 来释放必须在无论是否发生错误的情况下清理的资源（如文件句柄）。

### 示例

以下示例演示了所有四个子句。`process_record()` 函数针对不同条件引发 `Error`，调用者遍历 ID 列表以测试每个子句：

```mojo title="handle_error.mojo"
def process_record(id: Int) raises -> String:
    if id < 0:
        raise Error("invalid record ID: must be non-negative")
    if id > 999:
        raise Error("record not found")
    return String("record_", id)


def main() raises:
    try:
        for id in [5, 0, 1001, -3, 42]:
            var result: String
            try:
                print()
                print("try     => id:", id)
                if id == 0:
                    continue
                result = process_record(id)
            except e:
                if "invalid" in String(e):
                    print("except  => fatal:", e)
                    raise e^
                print("except  => handled:", e)
            else:
                print("else    => success:", result)
            finally:
                print("finally => done with id:", id)
    except e:
        print("\nre-raised error:", e)
```

```output

try     => id: 5
else    => success: record_5
finally => done with id: 5

try     => id: 0
finally => done with id: 0

try     => id: 1001
except  => handled: record not found
finally => done with id: 1001

try     => id: -3
except  => fatal: invalid record ID: must be non-negative
finally => done with id: -3

re-raised error: invalid record ID: must be non-negative
```

注意：

- 当 `id` 为 5 时：`process_record()` 成功，所以 `else` 运行，然后 `finally`。
- 当 `id` 为 0 时：`continue` 退出 `try` 代码块，跳过 `except` 和 `else`。只有 `finally` 运行。
- 当 `id` 为 1001 时：`process_record()` 引发错误。`except` 子句处理它，执行继续进行下一次迭代。
- 当 `id` 为 -3 时：`process_record()` 引发"无效"错误。`except` 子句使用 `raise e^` 重新引发它，将错误的所有权转移到外部的 `try`/`except`。`finally` 子句在错误传播之前仍然运行。由于重新引发退出了循环，`id` 42 永远不会被处理。

### 重新引发错误

要重新引发已捕获的错误，请使用带有 [转移符号](/docs/manual/values/ownership/#transfer-arguments-var-and/)（`^`）的 `raise` 来转移错误值的所有权：

```mojo
try:
    result = process_record(-1)
except e:
    print("Logging error:", e)
    raise e^  # 带所有权转移重新引发
```

您还可以从 `except` 子句中引发不同的错误。

## 类型化错误

对于需要比字符串消息更多的代码——如标准库 API、GPU 抽象或调用者需要结构化错误数据的情况——Mojo 允许您将自定义错误类型定义为 [结构体](/docs/manual/structs/)。

### 定义自定义错误类型

在 Mojo 中，任何结构体都可以作为错误类型——不需要特殊的基类或 trait。但是，建议实现 [`Writable`](/docs/std/format/Writable/) trait，以便在打印错误或程序因未处理的错误而终止时，错误会生成可读的消息：

```mojo
@fieldwise_init
struct ValidationError(Copyable, Writable):
    var field: String
    var reason: String

    def write_to(self, mut writer: Some[Writer]):
        writer.write("ValidationError(", self.field, "): ", self.reason)
```

[`@fieldwise_init`](/docs/reference/decorators/fieldwise-init/) 装饰器为每个字段生成一个参数的 `__init__()` 方法，因此您可以像 `ValidationError("username", "too short")` 或使用关键字参数如 `ValidationError(field="username", reason="too short")` 这样构造错误。

:::note

只要避免使用像 `String` 这样的堆分配类型，类型化错误就可以在 GPU 和嵌入式目标上工作。有关更多关于 GPU 编程的信息，请参阅 [GPU 基础](/docs/manual/gpu/fundamentals/)。

:::

### 引发类型化错误

要声明一个函数可以引发类型化错误，请在其签名中添加 `raises YourErrorType`：

```mojo
def validate_username(username: String) raises ValidationError -> String:
    if username.byte_length() == 0:
        raise ValidationError(field="username", reason="cannot be empty")
    if username.count_codepoints() < 3:
        raise ValidationError(
            field="username", reason="must be at least 3 characters"
        )
    return username
```

Mojo 函数默认是非引发函数。包含 `raises`（无论是否有类型）都会使其成为引发函数。每个函数最多可以声明一种错误类型。编译器强制执行此规则——如果函数体中的任何 `raise` 语句不匹配声明的类型，程序将无法编译。

如果非引发函数调用了引发函数，它必须在本地处理错误：

```mojo
# 这不会编译 — validate_username() 可以引发
def process_name(name: String):
    print(validate_username(name))

# 这会编译 — 错误已处理
def process_name_safe(name: String):
    try:
        print(validate_username(name))
    except e:
        print("Invalid:", e)
```

### 捕获类型化错误

使用 `try`/`except` 来捕获类型化错误。编译器会自动从被调用的函数推断错误类型，因此 `except e:` 给您一个完全类型化的错误值——无需转换：

```mojo
try:
    var name = validate_username("")
except e:
    # e 是一个 ValidationError — 直接访问字段
    print("Error in field '" + e.field + "': " + e.reason)
```

这会产生以下输出：

```output
Error in field 'username': cannot be empty
```

`try` 代码块只能包含一个 `except` 子句。Mojo 不支持 `except ErrorType as e:` 语法——类型总是从被调用的函数推断。

如果您需要处理引发不同错误类型的调用，请使用单独的 `try` 代码块：

```mojo
# 每个 try 代码块处理一种错误类型
try:
    var name = validate_username(input)
except e:
    # e 是一个 ValidationError — 直接访问字段
    print("Validation failed:", e.field, e.reason)

try:
    var file = open_file(path)
except e:
    # e 是一个 FileError — 在变体上匹配
    if e == FileError.not_found:
        print("Missing:", path)
```

:::note

如果您的错误类型实现了 [`Writable`](/docs/std/format/Writable/) trait，您也可以直接将 `e` 传递给 `print()`：

```mojo
except e:
    print(e)  # 调用 ValidationError.write_to()
```

这会产生以下输出：

```output
ValidationError(username): cannot be empty
```

:::

## 表示多种错误条件

每个函数在其 `raises` 子句中只能声明一种错误类型。当函数可以以多种不同方式失败时，您需要在一个类型中表示这些条件。Mojo 提供了两种方法：

- **枚举错误类型** — 使用 `comptime` 变体别名的单个结构体。当您只需要区分条件时，这更简单、更高效。
- **`Variant` 类型** — 带有每种条件单独结构体的标准库 [`Variant`](/docs/std/utils/variant/Variant/) 类型。当每种条件需要携带不同数据时，这更灵活。

### 枚举错误类型

单个结构体可以使用整数 `_variant` 字段和 [`comptime` 值](/docs/manual/metaprogramming/comptime-evaluation/#comptime-values)作为命名常量来表示所有错误条件。`write_to` 方法从变体代码生成人类可读的字符串：

```mojo
@fieldwise_init
struct FileError(Equatable, ImplicitlyCopyable, Writable):
    var _variant: Int

    # 编译时常量变体
    comptime not_found = FileError(_variant=1)
    comptime permission_denied = FileError(_variant=2)
    comptime already_exists = FileError(_variant=3)

    def variant_name(self) -> String:
        if self._variant == 1:
            return "not_found"
        elif self._variant == 2:
            return "permission_denied"
        elif self._variant == 3:
            return "already_exists"
        return "unknown"

    def write_to(self, mut writer: Some[Writer]):
        writer.write("FileError.", self.variant_name())
```

由于 `FileError` 有一个 `Int` 字段并符合 [`Equatable`](/docs/std/builtin/comparable/Equatable/)，编译器会自动合成 `__eq__()`，因此您可以直接比较变体：

```mojo
def open_file(path: String) raises FileError -> String:
    if not path:
        raise FileError.not_found
    if path == "/secret":
        raise FileError.permission_denied
    return "Contents of " + path
```

然后您可以在处理器中匹配特定的变体：

```mojo
try:
    print(open_file("/secret"))
except e:
    if e == FileError.not_found:
        print("Not found:", e)
    elif e == FileError.permission_denied:
        print("Permission denied:", e)
```

这会产生以下输出：

```output
Permission denied: FileError.permission_denied
```

### `Variant` 类型

当每个错误条件需要携带不同数据时，您可以使用标准库 [`Variant`](/docs/std/utils/variant/Variant/) 类型而不是基于整数的枚举。为每种条件定义一个单独的结构体，然后使用 `comptime` 别名将它们组合成一个错误类型：

```mojo title="variant_errors.mojo"
from std.utils import Variant


@fieldwise_init
struct NotFoundError(Copyable, Writable):
    var path: String

    def write_to(self, mut writer: Some[Writer]):
        writer.write("file not found: ", self.path)


@fieldwise_init
struct PermissionError(Copyable, Writable):
    var path: String
    var required_role: String

    def write_to(self, mut writer: Some[Writer]):
        writer.write(
            "permission denied on ",
            self.path,
            " (requires ",
            self.required_role,
            ")",
        )


comptime FileError = Variant[NotFoundError, PermissionError]
```

通过将内部错误包装在 `Variant` 类型中来构造 `Variant`：

```mojo
def open_file(path: String) raises FileError -> String:
    if not path:
        raise FileError(NotFoundError(""))
    if path == "/secret":
        raise FileError(PermissionError("/secret", "admin"))
    return "Contents of " + path
```

在处理器中，使用 `.isa[T]()` 测试发生了哪种条件，使用 `e[T]` 访问具有完整类型的内部错误：

```mojo
try:
    print(open_file("/secret"))
except e:
    if e.isa[NotFoundError]():
        print("Not found:", e[NotFoundError])
    elif e.isa[PermissionError]():
        print("Access denied:", e[PermissionError])
```

```output
Access denied: permission denied on /secret (requires admin)
```

当每个条件携带不同的字段时（如上面的 `path` 与 `path` + `required_role`），使用 `Variant` 方法。当您只需要区分条件而不需要为每种条件携带不同数据时，使用 [枚举错误类型](#enumerated-error-types) 模式。

## `Never` 类型

`Never` 是一个没有构造函数的类型——它无法实例化。这使得它在错误处理签名中用于表达两个相反的保证很有用：

- `raises YourErrorType -> Never` — 函数*总是*引发，从不返回值。这对于像 `panic()` 这样的函数很有用，它们无条件地发出错误信号。
- `raises Never -> ReturnType` — 函数*从不*引发，总是返回值。这相当于完全省略 `raises`。

### 总是引发错误的函数

返回类型为 `-> Never` 的函数必须永远不会以 `return` 语句终止——它必须在每个代码路径上引发（或无限循环）。由于 `Never` 可以替代任何类型，编译器允许用这样的函数代替返回值：

```mojo
# 总是引发，从不返回
def panic(msg: String) raises -> Never:
    raise Error(msg)

def get_value_or_panic(maybe: Optional[Int]) raises -> Int:
    if maybe:
        return maybe.value()
    # Never 在此分支中替代 Int
    panic("value is missing")
```

### 从不引发错误的函数

具有 `raises Never` 的函数在编译时保证从不引发。这相当于编写一个普通的非引发函数：

```mojo
# 这两个签名是等价的：
def safe_add(a: Int, b: Int) raises Never -> Int:
    return a + b

def safe_add(a: Int, b: Int) -> Int:
    return a + b
```

这种等价性在与 [参数化引发](#parametric-raises) 结合使用时特别有用，当函数参数不引发时，编译器会推断 `raises Never`。

## 参数化引发

您可以编写 [泛型函数](/docs/manual/parameters/#parameters-and-generics) 将错误类型从函数参数传播到调用者。这使用错误类型的编译时参数：

```mojo
def run_action[
    ErrorType: AnyType
](action: def() thin raises ErrorType -> Int) raises ErrorType -> Int:
    return action()
```

函数类型使用 `thin`，因为 `action` 是一个非捕获函数值。

`ErrorType` 参数从您传入的函数推断。如果函数引发 `NetworkError`，则 `run_action` 引发 `NetworkError`。如果函数引发 `ParseError`，则 `run_action` 引发 `ParseError`：

```mojo
def fetch_data() raises NetworkError -> Int:
    raise NetworkError(code=404)

def parse_config() raises ParseError -> Int:
    raise ParseError(position=42)

# ...

# ErrorType 推断为 NetworkError
try:
    _ = run_action(fetch_data)
except e:
    print("Network failure:", e)

# ErrorType 推断为 ParseError
try:
    _ = run_action(parse_config)
except e:
    print("Parse failure:", e)
```

如果函数参数根本不引发，编译器会推断 `Never` 为错误类型。这意味着 `run_action` 本身成为非引发函数，不需要 `try` 代码块：

```mojo
def get_value() -> Int:
    return 99

# ...

# ErrorType 推断为 Never — 不需要 try 代码块
var result = run_action(get_value)
print("Got value:", result)
```

这会产生以下输出：

```output
Got value: 99
```

## 类型化错误和 `Error` 交互

大多数代码库包含混合了引发、不引发或引发类型化错误的函数。本节介绍这些风格如何交互以及如何有效地使用它们。

### 在 API 边界包装 `Error`

当从使用类型化错误的函数调用引发函数或其他 `Error` 引发代码时，捕获 `Error` 并转换它：

```mojo
def validate_with_error(value: Int) raises -> Int:
    if value < 0:
        raise "value cannot be negative"
    return value

def wrapped_validate(value: Int) raises ValidationError -> Int:
    try:
        return validate_with_error(value)
    except e:
        raise ValidationError(field="value", reason=String(e))
```

### 避免与类型化错误一起使用裸 `raises`

在调用类型化错误函数的函数上使用裸 `raises`（不带类型）会导致*类型擦除*——编译器忘记特定的错误类型，即使运行时保留错误的身份：

```mojo
# 反模式：裸 raises 在编译时擦除类型信息
def validate_bare_raises(value: Int) raises -> Int:
    return validate_typed(value)
```

`validate_bare_raises()` 的调用者接收到 `Error`，而不是 `ValidationError`：

```mojo
try:
    _ = validate_bare_raises(-5)
except e:
    # e 被类型化为 Error — 没有字段访问可用
    # e.field 在这里不会编译
    print(e)
```

```output
ValidationError(value): cannot be negative
```

错误消息仍然显示 `ValidationError`，因为运行时保留原始错误的 [`Writable`](/docs/std/format/Writable/) 输出。但编译器只看到 `Error`，因此您失去了对结构化字段的访问。始终使用 `raises YourErrorType` 以维护类型安全。

请注意，类型擦除只影响通过裸 `raises` 函数传播的*未捕获*错误。如果您在本地捕获类型化错误，您仍然可以获得完整的字段访问：

```mojo
def error_caller():
    try:
        _ = validate_typed(-5)
    except e:
        # e 是一个 ValidationError — 字段访问有效
        print("Field:", e.field, "Reason:", e.reason)
```

```output
Field: value Reason: cannot be negative
```

### 不要在单个 `try` 代码块中混合错误类型

您不能在同一个 `try` 代码块中调用引发不同错误类型的函数。编译器会拒绝这种不匹配：

```mojo
def error_func() raises -> Int:
    raise "something went wrong"

def typed_func() raises ValidationError -> Int:
    raise ValidationError(field="x", reason="invalid")

# 这不会编译
def mixed() raises ValidationError:
    try:
        _ = error_func()   # 引发 Error
        _ = typed_func()    # 引发 ValidationError
    except e:
        print(e)
```

编译器报告：

```output
error: cannot call function that may raise 'Error' in a context that
supports an error type of 'ValidationError'
```

要调用这两个函数，请使用单独的 `try` 代码块或按照 [在 API 边界包装 `Error`](#wrap-error-at-api-boundaries) 中所示包装 `Error` 引发函数。

### 混合代码库的建议

当同时使用 `Error` 和类型化错误时：

- **使用 `raises YourErrorType`** — 始终在函数签名中指定错误类型。裸 `raises` 会丢弃类型信息。
- **使用单独的 `try` 代码块** — 当调用具有不同错误类型的函数时，使用嵌套或顺序的 `try` 代码块来独立处理每种类型。

:::note

有关这些交互模式的完整工作示例，请参阅 [`error_interaction.mojo`](https://github.com/modular/modular/blob/main/mojo/docs/code/manual/errors/error_interaction.mojo)。

:::

## 为错误启用堆栈跟踪生成

由于 Mojo 将错误表示为替代返回值而不是栈展开异常，堆栈跟踪收集不是自动的。收集堆栈跟踪需要堆分配并增加运行时开销，因此默认情况下禁用它以保持错误处理轻量级。

:::important

堆栈跟踪是内置 `Error` 类型的功能。类型化错误目前不捕获堆栈跟踪，因为跟踪是在 `Error.__init__()` 内部收集的，而自定义错误结构体没有等效的钩子。本节中的所有示例都故意使用 `Error`。

:::

当您的程序遇到段错误时，Mojo 会生成堆栈跟踪。但是，默认情况下，当您的程序引发错误时，Mojo *不会*生成堆栈跟踪——这避免了额外的运行时开销。要为引发的错误启用堆栈跟踪，请将 `MODULAR_DEBUG` 环境变量设置为 `stack-trace-on-error`，如下面的示例所示。

请记住，当使用 [`mojo build`](/docs/cli/build/) 编译程序时，编译器默认会优化并剥离符号，因此您的堆栈跟踪通常不会很有用。

考虑这个程序：

```mojo title="stacktrace_error.mojo"
def func2() raises -> None:
    raise Error("Intentional error")


def func1() raises -> None:
    func2()


def main() raises:
    func1()
```

如果您使用默认设置编译程序并设置环境变量运行它，您将看到一个没有符号的堆栈跟踪：

```sh
mojo build stacktrace_error.mojo
```

```sh
MODULAR_DEBUG=stack-trace-on-error ./stacktrace_error
```

```output
#0 0x... llvm::sys::PrintStackTrace(llvm::raw_ostream&, int)
#1 0x... KGEN_CompilerRT_GetStackTrace
#2 0x... main (./stacktrace_error+...)

Unhandled exception caught during execution: Intentional error
```

要生成更有用的堆栈跟踪，请使用 `--debug-level full`（或 `-g`）编译程序以包含调试符号：

```sh
mojo build --debug-level full stacktrace_error.mojo
```

```sh
MODULAR_DEBUG=stack-trace-on-error ./stacktrace_error
```

```output
#0 0x... llvm::sys::PrintStackTrace(llvm::raw_ostream&, int)
#1 0x... KGEN_CompilerRT_GetStackTrace
#2 0x... Error.__init__[...](...) .../builtin/error.mojo:159:38
#3 0x... stacktrace_error::func2() stacktrace_error.mojo:14:16
#4 0x... stacktrace_error::func1() stacktrace_error.mojo:18:10
#5 0x... stacktrace_error::main() stacktrace_error.mojo:22:10
#6 0x... __wrap_and_execute_raising_main[...](...) .../builtin/_startup.mojo:88:18
#7 0x... main .../builtin/_startup.mojo:103:4

Unhandled exception caught during execution: Intentional error
```

有了调试符号，跟踪显示了函数调用链和源位置：`main()` → `func1()` → `func2()` → `Error.__init__()`。

:::note

直接使用 [`mojo run`](/docs/cli/run/) 或 `mojo` 运行程序不会在堆栈跟踪中包含调试符号，即使使用 `--debug-level full`。请使用带有 `-g` 的 `mojo build` 并运行编译后的二进制文件以获取符号化的堆栈跟踪。

:::

### 程序化捕获堆栈跟踪

您可以将 `Error` 实例绑定到 `except` 子句中的变量，并调用其 [`get_stack_trace()`](/docs/std/builtin/error/Error/#get_stack_trace) 方法以 `Optional[String]` 形式获取堆栈跟踪。如果禁用或不可用堆栈跟踪收集，该方法返回 `None`：

```mojo title="stacktrace_error_capture.mojo"
def func2() raises -> None:
    raise Error("Intentional error")


def func1() raises -> None:
    func2()


def main() raises:
    try:
        func1()
    except e:
        print(e)
        print("-" * 20)
        var stack_trace = e.get_stack_trace()
        if stack_trace:
            print(stack_trace.value())
        else:
            print("No stack trace available")
```

当您使用调试符号编译并启用堆栈跟踪生成运行时：

```sh
mojo build --debug-level full stacktrace_error_capture.mojo
```

```sh
MODULAR_DEBUG=stack-trace-on-error ./stacktrace_error_capture
```

```output
Intentional error
--------------------
#0 0x... llvm::sys::PrintStackTrace(llvm::raw_ostream&, int)
#1 0x... KGEN_CompilerRT_GetStackTrace
#2 0x... Error.__init__[...](...) .../builtin/error.mojo:159:38
#3 0x... stacktrace_error_capture::func2() stacktrace_error_capture.mojo:14:16
#4 0x... stacktrace_error_capture::func1() stacktrace_error_capture.mojo:18:10
#5 0x... stacktrace_error_capture::main() stacktrace_error_capture.mojo:23:14
#6 0x... __wrap_and_execute_raising_main[...](...) .../builtin/_startup.mojo:88:18
#7 0x... main .../builtin/_startup.mojo:103:4
```

如果不启用堆栈跟踪生成，输出为：

```output
Intentional error
--------------------
No stack trace available
```

## 使用上下文管理器

*上下文管理器* 是一个管理资源（如文件、网络连接和数据库连接）的对象。它提供了一种分配资源并在不再需要时自动释放它们的方法，确保正确清理并在发生错误时防止资源泄漏。

:::note

上下文管理器既适用于类型化错误也适用于内置 `Error` 类型。`with` 语句透明地处理这两种错误风格。

:::

作为示例，考虑从文件读取数据。一种朴素的方法可能看起来像这样：

```mojo
# 获取文件句柄以从存储读取
f = open(input_file, "r")
content = f.read()
# 按需处理内容
# 关闭文件句柄
f.close()
```

调用 [`close()`](/docs/std/io/file/FileHandle/#close) 会释放与打开的文件关联的内存和其他操作系统资源。如果您的程序打开许多文件而不关闭它们，可能会耗尽程序可用的资源并导致错误。如果您是写入文件而不是从文件读取，问题会更严重，因为操作系统可能会将输出缓冲到内存中，直到文件关闭。如果您的程序崩溃而不是正常退出，该缓冲数据可能会丢失而不是写入存储。

上面的示例包含了对 `close()` 的调用，但它忽略了 [`read()`](/docs/std/io/file/FileHandle/#read) 可能引发错误的可能性，这将阻止 `close()` 执行。要处理这种情况，您可以重写代码以使用 `try`，如下所示：

```mojo
# 获取文件句柄以从存储读取
f = open(input_file, "r")

try:
    content = f.read()
    # 按需处理内容
finally:
    # 确保即使 read() 引发错误，文件句柄也会关闭
    f.close()
```

然而，[`open()`](/docs/std/io/file/open/) 返回的 [`FileHandle`](/docs/std/io/file/FileHandle/) 结构体是一个上下文管理器。当与 Mojo 的 `with` 语句一起使用时，上下文管理器确保它管理的资源在代码块结束时正确释放，即使发生错误。对于 `FileHandle`，这意味着 `close()` 调用自动发生。因此，您可以重写上面的示例以利用上下文管理器（并省略对 `close()` 的显式调用），如下所示：

```mojo
with open(input_file, "r") as f:
    content = f.read()
    # 按需处理内容
```

`with` 语句还允许您在同一个代码块中使用多个上下文管理器。作为示例，以下代码打开一个文本文件，读取其全部内容，将其转换为大写，然后将结果写入不同的文件：

```mojo
with open(input_file, "r") as f_in, open(output_file, "w") as f_out:
    input_text = f_in.read()
    output_text = input_text.upper()
    f_out.write(output_text)
```

`FileHandle` 可能是最常用的上下文管理器。Mojo 标准库中上下文管理器的其他示例是 [`NamedTemporaryFile`](/docs/std/tempfile/tempfile/NamedTemporaryFile/)、[`TemporaryDirectory`](/docs/std/tempfile/tempfile/TemporaryDirectory/)、[`BlockingScopedLock`](/docs/std/utils/lock/BlockingScopedLock/) 和 [`assert_raises`](/docs/std/testing/testing/assert_raises/)。您还可以创建自己的自定义上下文管理器，如本节后面的 [编写自定义上下文管理器](#write-a-custom-context-manager) 中所述。

## 编写自定义上下文管理器

编写自定义上下文管理器就是定义一个实现两个特殊 *dunder* 方法（"双下划线"方法）：`__enter__()` 和 `__exit__()` 的 [结构体](/docs/manual/structs/)：

- `__enter__()` 由 `with` 语句调用以进入运行时上下文。`__enter__()` 方法应该初始化上下文所需的任何状态并返回上下文管理器。

- `__exit__()` 在 `with` 代码块完成执行时调用，即使 `with` 代码块通过 `continue`、`break` 或 `return` 终止。`__exit__()` 方法应该释放与上下文关联的任何资源。在 `__exit__()` 方法返回后，上下文管理器被销毁。

  如果 `with` 代码块引发错误，则 `__exit__()` 方法在任何错误处理发生之前运行（即，在被 `try`/`except` 结构捕获或程序终止之前）。如果您想在 `with` 代码块中为错误条件定义条件处理，可以实现一个重载版本的 `__exit__()`，它接受一个错误参数。有关更多信息，请参阅下面的 [定义条件 `__exit__()` 方法](#define-a-conditional-__exit__-method) 和 [在 `__exit__()` 中处理类型化错误](#handle-typed-errors-in-__exit__)。

  对于不需要在终止时释放资源或执行其他操作的上下文管理器，不需要实现 `__exit__()` 方法。在这种情况下，上下文管理器在 `with` 代码块完成执行后自动销毁。

下面是实现 `Timer` 上下文管理器的示例，它打印执行 `with` 代码块所花费的时间：

```mojo title="context_mgr.mojo"
import std.sys
import std.time

@fieldwise_init
struct Timer(ImplicitlyCopyable):
    var start_time: Int

    def __init__(out self):
        self.start_time = 0

    def __enter__(mut self) -> Self:
        self.start_time = Int(time.perf_counter_ns())
        return self

    def __exit__(mut self):
        end_time = time.perf_counter_ns()
        elapsed_time_ms = round(
            Float64(end_time - UInt(self.start_time)) / 1e6, 3
        )
        print("Elapsed time:", elapsed_time_ms, "milliseconds")

def main() raises:
    with Timer():
        print("Beginning execution")
        time.sleep(1.0)
        if len(sys.argv()) > 1:
            raise "simulated error"
        time.sleep(1.0)
        print("Ending execution")
```

运行此示例会产生如下输出：

```sh
mojo context_mgr.mojo
```

```output
Beginning execution
Ending execution
Elapsed time: 2010.0 milliseconds
```

```sh
mojo context_mgr.mojo fail
```

```output
Beginning execution
Elapsed time: 1002.0 milliseconds
Unhandled exception caught during execution: simulated error
```

### 定义条件 `__exit__()` 方法

创建上下文管理器时，可以实现 `__exit__(self)` 形式的 `__exit__()` 方法来处理 `with` 语句在任何情况下（包括错误）的完成。但是，您可以选择额外实现一个重载版本，当 `with` 代码块中发生 `Error` 时调用：

```mojo
def __exit__(self, error: Error) raises -> Bool
```

给定作为参数发生的 `Error`，该方法可以执行以下任何操作：

- 返回 `True` 以抑制错误。
- 返回 `False` 以重新引发错误。
- 引发新错误。

以下是一个上下文管理器的示例，它只抑制特定的错误条件并传播所有其他错误：

```mojo title="conditional_context_mgr.mojo"
import std.time

@fieldwise_init
struct ConditionalTimer(ImplicitlyCopyable):
    var start_time: Int

    def __init__(out self):
        self.start_time = 0

    def __enter__(mut self) -> Self:
        self.start_time = Int(time.perf_counter_ns())
        return self

    def __exit__(mut self):
        end_time = time.perf_counter_ns()
        elapsed_time_ms = round(
            Float64(end_time - UInt(self.start_time)) / 1e6, 3
        )
        print("Elapsed time:", elapsed_time_ms, "milliseconds")

    def __exit__(mut self, e: Error) -> Bool:
        if String(e) == "just a warning":
            print("Suppressing error:", e)
            self.__exit__()
            return True
        else:
            print("Propagating error")
            self.__exit__()
            return False

def flaky_identity(n: Int) raises -> Int:
    if (n % 4) == 0:
        raise "really bad"
    elif (n % 2) == 0:
        raise "just a warning"
    else:
        return n

def main() raises:
    for i in range(1, 9):
        with ConditionalTimer():
            print("\nBeginning execution")

            print("i =", i)
            time.sleep(0.1)

            if i == 3:
                print("continue executed")
                continue

            j = flaky_identity(i)
            print("j =", j)

            print("Ending execution")
```

运行此示例会产生此输出：

```output

Beginning execution
i = 1
j = 1
Ending execution
Elapsed time: 105.0 milliseconds

Beginning execution
i = 2
Suppressing error: just a warning
Elapsed time: 106.0 milliseconds

Beginning execution
i = 3
continue executed
Elapsed time: 106.0 milliseconds

Beginning execution
i = 4
Propagating error
Elapsed time: 106.0 milliseconds
Unhandled exception caught during execution: really bad
```

### 在 `__exit__()` 中处理类型化错误

`__exit__(self, error: Error)` 重载只处理 `Error` 值。要处理类型化错误，请实现一个带有编译时错误类型参数的通用 `__exit__()` 方法：

```mojo
def __exit__[ErrType: AnyType](self, err: ErrType) -> Bool
```

此方法直接接收类型化错误，保留其完整的类型信息。您可以使用 [反射](/docs/manual/metaprogramming/reflection/) 在编译时检查错误类型。例如，您可以：

- `reflect[ErrType].name()` — 获取错误类型的名称作为字符串。
- `comptime if conforms_to(ErrType, Writable)` — 检查错误是否实现了 `Writable`。
- `trait_downcast[Writable](err)` — 通过其 `Writable` 接口访问错误。

以下 `ResourceGuard` 示例演示了此模式：

```mojo
from std.reflection import *

@fieldwise_init
struct ConnectionError(Copyable, Writable):
    var message: String

    def write_to(self, mut writer: Some[Writer]):
        writer.write("ConnectionError: ", self.message)


struct ResourceGuard(ImplicitlyCopyable):
    var name: String
    var suppress_errors: Bool

    def __init__(out self, name: String, suppress_errors: Bool = False):
        self.name = name
        self.suppress_errors = suppress_errors

    def __enter__(self) -> Self:
        print("Acquiring:", self.name)
        return self

    def __exit__(self):
        print("Releasing:", self.name, "(no error)")

    def __exit__[ErrType: AnyType](self, err: ErrType) -> Bool:
        comptime type_name = reflect[ErrType].name()
        print("Releasing:", self.name)
        print("  Error type:", type_name)

        comptime if conforms_to(ErrType, Writable):
            print("  Message:", trait_downcast[Writable](err))

        return self.suppress_errors
```

当没有错误发生时，`__exit__(self)` 按照正常方式运行。当发生类型化错误时，`__exit__[ErrType]()` 运行，让您访问错误类型及其数据：

```mojo
# 没有错误 — 调用 __exit__(self)
with ResourceGuard("database"):
    print("Working...")

# 类型化错误，已抑制 — __exit__[ErrType] 返回 True
with ResourceGuard("cache", suppress_errors=True):
    use_connection()  # 引发 ConnectionError
print("Continued after suppressed error")
```

```output
Acquiring: database
Working...
Releasing: database (no error)

Acquiring: cache
Releasing: cache
  Error type: ConnectionError
  Message: ConnectionError: connection timed out
Continued after suppressed error
```

:::note

有关包括错误抑制和传播的完整工作示例，请参阅 [`resource_guard.mojo`](https://github.com/modular/modular/blob/main/mojo/docs/code/manual/errors/resource_guard.mojo)。

:::
