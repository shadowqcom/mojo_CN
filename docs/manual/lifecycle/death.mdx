一旦值/对象不再被使用，Mojo 就会销毁它。Mojo *不会*等到代码块结束——甚至不会等到表达式结束——才销毁未使用的值。它采用"尽快销毁"（ASAP）的销毁策略，在每个子表达式之后运行。即使在像 `a+b+c+d` 这样的表达式中，Mojo 也会在中间值不再需要时立即销毁它们。

Mojo 在编译时使用静态分析来确定值的最后一次使用。在那一刻，它会立即结束该值的生命周期并调用*隐式* `__deinit__()` 反初始化器（deinitializer）。你可以在结构体中重写 `__deinit__()` 来执行任何所需的清理。

:::note
对于需要更强保证的类型，Mojo 还支持*显式*由编译器检查的反初始化器，它们为管理清理提供了额外的安全层。有关详细信息，请阅读下文关于[显式销毁](#explicitly-destroyed-types)的内容。
:::

例如，请注意 `Balloon` 的每个实例在何时调用 `__deinit__()` 反初始化器：

```mojo
@fieldwise_init
struct Balloon(Writable):
    var color: String

    def write_to(self, mut writer: Some[Writer]):
        writer.write(String("a ", self.color, " balloon"))

    def __deinit__(deinit self):
        print("Destroyed", String(self))


def main():
    var a = Balloon("red")
    var b = Balloon("blue")
    print(a)
    # a.__deinit__() runs here for "red" Balloon

    a = Balloon("green")
    # a.__deinit__() runs immediately because "green" Balloon is never used

    print(b)
    # b.__deinit__() runs here
```

```output
a red balloon
Destroyed a red balloon
Destroyed a green balloon
a blue balloon
Destroyed a blue balloon
```

每个值的初始化都会与一次反初始化器调用配对，而 `a` 实际上会被销毁多次——每次它接收新值时都会被销毁一次。

还请注意，这个 `__deinit__()` 实现实际上不做任何事情。大多数结构体不需要自定义反初始化器，如果你不定义，Mojo 会自动添加一个空操作的反初始化器。

`__deinit__()` 方法使用 `deinit` [参数约定](/docs/manual/values/ownership/#argument-conventions)接收其参数，这表明该值正在被反初始化。

## 默认反初始化器行为

你可能想知道 Mojo 如何在没有自定义反初始化器的情况下销毁一个类型，或者为什么空操作的反初始化器有用。如果一个类型只是字段的集合，就像 `Balloon` 示例那样，Mojo 只需要销毁这些字段：`Balloon` 不会动态分配内存，也不会使用任何长生命周期的资源（比如文件句柄）。当 `Balloon` 值被销毁时，不需要采取任何特殊操作。

当 `Balloon` 值被销毁时，其 `color` 字段中的 `String` 值不再被使用，因此也会立即被销毁。

`String` 值要稍微复杂一些。Mojo 字符串是可变的。`String` 对象有一个内部缓冲区——一个 [`List`](/docs/std/collections/list/List/) 字段，用于保存组成字符串的字符。`List` 将其内容存储在堆上动态分配的内存中，因此字符串可以。字符串本身没有任何特殊的反初始化器逻辑，但当 Mojo 销毁一个字符串时，它会调用 `List` 字段的反初始化器，由它来释放内存。

由于 `String` 不需要任何自定义反初始化器逻辑，它有一个空操作的反初始化器：字面意义上就是一个不做任何事情的 `__deinit__()` 方法。这看似毫无意义，但它意味着 Mojo 可以在任何值的生命周期结束时调用其反初始化器。这使得编写类型泛型的容器和算法更加容易。

### ASAP 销毁的益处

与其他语言类似，Mojo 遵循这样一个原则：对象/值在初始化器（`__init__()`）中获取资源，并在反初始化器（`__deinit__()`）中释放资源。然而，与基于作用域的销毁（例如 C++ 的 [RAII 模式](https://en.cppreference.com/w/cpp/language/raii)，它会等到代码作用域结束时才销毁值）相比，Mojo 的 ASAP 销毁具有一些优势：

- 在最后一次使用时立即销毁值，可以很好地与"移动"优化配合，后者将"复制+del"对转换为一次"移动"操作。

- 在 C++ 中，在作用域结束时销毁值对于尾递归等某些常见模式是有问题的，因为析构函数调用发生在尾调用之后。这对某些函数式编程模式可能构成重大的性能和内存问题，而在 Mojo 中这并不是问题，因为析构函数调用总是发生在尾调用之前。

Mojo 的销毁策略更类似于 Rust 和 Swift 的工作方式，因为它们都具备强值所有权跟踪并提供内存安全。一个区别在于，Rust 和 Swift 需要使用[动态"drop flag"](https://doc.rust-lang.org/nomicon/drop-flags.html)——它们维护隐藏的影子变量来跟踪值的状态以提供安全性。这些变量通常会被优化掉，但 Mojo 的方法完全消除了这种开销，使生成的代码更快并避免了歧义。

## 隐式反初始化器

Mojo 会在值的最后一次使用之后调用该值的反初始化器，除非该类型通过 `Deinitable where False` 退出了 `Deinitable`。这个 trait 提供了一个默认的空操作反初始化器（`__deinit__()`），你可以重写它。

对于隐式反初始化器，可以创建自定义的 `__deinit__()` 实现来执行任何所需的清理。这可能包括释放动态分配的内存（例如通过 `dealloc()`）或释放长生命周期的资源，比如文件句柄。

对于只是其他类型简单集合的类型，通常不需要重写 `__deinit__()`。

例如，考虑这个简单的结构体：

```mojo
@fieldwise_init
struct Balloons:
    var color: String
    var count: Int
```

这里不需要定义 `__deinit__()` 反初始化器，因为它只是其他类型（`String` 和 `Int`）的简单集合，并且它不会动态分配内存。

而下面的结构体分配了内存，因此它必须定义 `__deinit__()` 方法来释放该内存。此处使用的 [`ThinAllocation`](/docs/std/memory/alloc/ThinAllocation/) 类型是指向已分配内存的句柄。

```mojo
from std.memory import alloc, dealloc, ThinAllocation

struct HeapArray(Writable):
    var data: ThinAllocation[Int]
    var size: Int

    def __init__(out self, *values: Int):
        self.size = len(values)
        self.data = alloc[Int]({count = self.size}).into_thin()
        var ptr = self.data.unsafe_ptr()
        for i in range(self.size):
            ptr.unsafe_offset(i).unsafe_write(values[i])

    def write_to(self, mut writer: Some[Writer]):
        writer.write("[")
        var ptr = self.data.unsafe_ptr()
        for i in range(self.size):
            writer.write(ptr[unsafe_offset=i])
            if i < self.size - 1:
                writer.write(", ")
        writer.write("]")

    def __deinit__(deinit self):
        print("Destroying", self.size, "elements")
        var ptr = self.data.unsafe_ptr()
        for i in range(self.size):
            ptr.unsafe_offset(i).unsafe_deinit_pointee()
        dealloc(self.data^.unsafe_with_layout({count = self.size}))

def main():
    var a = HeapArray(10, 1, 3, 9)
    print(a)
```

```output
[10, 1, 3, 9]
Destroying 4 elements
```

该反初始化器使用 `deinit` [参数约定](/docs/manual/values/ownership#argument-conventions)接收其 `self` 参数，该约定授予对该值的独占所有权，并在函数结束时将其标记为已销毁。（有关 `deinit` 约定的更多信息，请参阅[实例初始化](/docs/manual/lifecycle/initialization/)）。

请注意，指针并不*拥有*它所指向内存中的任何值，因此当指针被销毁时，Mojo 不会调用这些值的反初始化器。同样，分配（allocation）是内存的句柄，但它并不拥有存储在该内存中的值。

因此，在上面的 `HeapArray` 示例中，调用 `dealloc()` 会释放内存，但不会调用已存储值的反初始化器。这就是为什么反初始化器先遍历这些元素，调用 `Pointer` 类型提供的 `unsafe_deinit_pointee()` 方法，然后再进行释放。

:::note
你不应该显式调用反初始化器。如果你需要确保在特定位置调用反初始化器，请使用[显式生命周期扩展](#explicit-lifetime-extension)中描述的丢弃（discard）模式。
:::

需要注意的是，`__deinit__()` 方法是一个"额外"的清理事件，你的实现并不会覆盖任何默认的反初始化行为。例如，即使你添加了一个什么都不做的 `__deinit__()` 方法，Mojo 仍然会销毁 `Balloons` 中的所有字段：

```mojo
@fieldwise_init
struct Balloons:
    var color: String
    var count: Int

    def __deinit__(deinit self):
        # Mojo destroys all the fields when they're last used
        pass
```

然而，`__deinit__()` 反初始化器内部的 `self` 值仍然是完整的（因此所有字段仍然可用），直到反初始化器返回。

## 显式销毁的类型

Mojo 同时支持隐式和显式的值销毁。每种方式都在安全性、性能和开销之间平衡不同的需求：

```mojo
# All type are Deinitable by default
struct MyType: # ...

# Explicitly declare the conformance
struct MyType(Deinitable): # ...

# Explicit destruction. Disables the default deinitializer `__deinit__()`
struct MyType(Deinitable where False): # ...

# Use a message to explain other destruction paths
struct MyType(Deinitable where(False, "Must call cleanup()")): # ...
```

理解显式销毁类型的一种方式是，它们创建了一个未来的需求，一个行动的承诺。创建一个实例就意味着你承诺在该值不再被使用时执行特定的操作（例如刷新、关闭、提交或丢弃）。

这种"控制未来"的能力对开发者而言是一个强大的工具。它允许将拆卸要求直接添加到类型系统中。它引导用户走向有效的清理路径，使跳过这些路径的程序无法编译，并将安全销毁提升为值生命周期中一等公民的部分。

采用*隐式销毁*时，编译器负责管理清理。它会基于生命周期分析，在值不再被使用时自动调用 `__deinit__()`。你不需要自己调用反初始化器。

采用*显式销毁*时，你接管清理职责。你必须定义并调用一个命名的清理方法（例如 `cleanup()` 或 `save_and_close()`），并且必须在该值所在作用域结束之前调用该清理方法。编译器会禁用自动反初始化器。它要求你消耗该值。如果不这样做，会导致编译错误。

### 构建显式销毁

要将一个类型标记为显式销毁，需在该类型的声明中加入 `Deinitable where False` 一致性。这会禁用自动销毁，并要求你定义并调用一个命名的清理方法。

定义一个接收 `deinit self` 参数的方法。这会为你的反初始化器启用编译时检查，并为你提供空间来添加必须在销毁之前执行的操作。

与 `__deinit__()` 方法不同，命名的反初始化器可以引发错误。这在处理清理失败时为调用方提供了支持。

因为 `deinit self` 即使在错误路径上也会消耗该值，所以调用方不能再在同一实例上调用另一个反初始化器：

```mojo
struct FileBuffer(Deinitable where False):
    var path: String
    var data: String

    def __init__(out self, path: String):
        self.path = path
        self.data = ""

    def write(mut self, content: String):
        self.data += content

    # Choose one cleanup path from these two options
    def save_and_close(deinit self) raises:
        write_to_disk(self.path, self.data)

    def discard(deinit self):
        # Abandon buffered data without writing
        pass
```

使用时，你必须调用其中一个反初始化器：

```mojo
def write_log(path: String, message: String) raises:
    var buffer = FileBuffer(path)
    buffer.write(message)
    buffer^.save_and_close()  # Required: explicit destruction
```

编译器会验证每个显式销毁的值是否都调用了反初始化器，如果找不到，则会发出关于被放弃的值的错误。如果你提供了自定义消息，该消息会出现在错误输出中：

```mojo
struct CustomFileHandle(
    Deinitable where(False, "Must call save_and_close() or discard()")
):

# ...
```

### 何时使用显式销毁

当清理无法自动处理且必须在代码中加以控制时，请选择显式销毁。常见情形包括：

- 清理可能失败并需要错误处理。
- 可能存在多条清理路径。
- 清理操作的顺序很重要。
- 清理开销较大，应当是有意为之。

示例：

```mojo
# Multiple cleanup paths
struct Transaction(
    Deinitable where(False, "Use commit() or rollback()")
)
    def commit(deinit self) raises:  # Offers error handling
        # ...

    def rollback(deinit self):
        # ...

# Order matters
struct MutexGuard(Deinitable where False):
    # Must be called to release the lock before other operations
    def unlock(deinit self):
        # ...

# Cleanup is expensive
struct BatchProcessor(Deinitable where False):
    # Expensive operation user should explicitly trigger
    def finalize(deinit self) raises:
        # ...
```

### 参数化代码中的显式销毁

以 `AnyType` 参数化的代码既可以接受 `Deinitable` 的值，也可以接受显式销毁的值。但是，它无法自动销毁需要显式销毁的值。

显式反初始化器是特定于其类型的。类型泛型代码无法命名或调用它们，除非该类型受到约束：

```mojo
def parameterized_function_1[T: AnyType](var value: T):
    pass  # Error: value abandoned here

def parameterized_function_2[T: Deinitable](var value: T):
    # OK: T can be implicitly destroyed
    pass  # value.__deinit__() called automatically
```

如果参数化函数可能会消耗其参数，那么它必须确保该值在其生命周期结束时能够被安全销毁。参数化代码无法调用类型特定的显式反初始化器，除非该行为受到约束。请从以下方式中选择一种：

- 通过可变或不可变引用而不是通过所有权来接受值，使函数不会消耗它。
- 返回该值或转移所有权而不是消耗它。
- 通过 `Deinitable` trait 要求隐式销毁，这保证 `__deinit__()` 反初始化器可用并能够被自动调用：

  ```mojo
  def parameterized_function_3[T: Deinitable](var value: T):
      pass  # value.__deinit__() called automatically
  ```

## `deinit` 参数约定

在方法中，将 `deinit` 约定加到 `self` 上意味着该方法在返回时会完全消耗该值。具体而言，`deinit self` 表示：

- 方法获取 `self` 的所有权。
- 方法返回之后不会调用任何自动反初始化器。
- 可以在方法内部转移或显式销毁字段。
- 可能在方法内部进行额外的清理工作。
- 当方法完成时，该值被视为已销毁。

```mojo
struct Example(Deinitable where False):
    var field: String

    def consume_example(deinit self, mut other: Self):
        # Can transfer field values
        other.field = self.field^
        # No automatic deinitializer called
        # self is considered destroyed when method returns
```

用 `deinit self` 标记的方法可以将 `self` 的所有权转移给其他 `deinit` 方法。链式反初始化方法允许将清理职责进行委托和集中：

```mojo
def cleanup_method1(deinit self):
    # perform some cleanup tasks here
    self^.cleanup_method2()  # delegate to specialized method

def cleanup_method2(deinit self):
    # Perform shared cleanup duties
    pass
```

## 字段生命周期

除了跟踪程序中所有对象的生命周期之外，Mojo 还会独立跟踪结构体的每个字段。也就是说，Mojo 会跟踪"整个对象"是完全初始化/销毁还是部分初始化/销毁，并使用其 ASAP 销毁策略独立地销毁每个字段。

例如，考虑这段更改字段值的代码：

```mojo
@fieldwise_init
struct Balloons:
    var color: String
    var count: Int


def main():
    var balloons = Balloons("red", 5)
    print(balloons.color)
    # balloons.color.__deinit__() runs here, because this instance is
    # no longer used; it's replaced below

    balloons.color = "blue"  # Overwrite balloons.color
    print(balloons.color)
    # balloons.__deinit__() runs here
```

`balloons.color` 字段在第一个 `print()` 之后被销毁，因为 Mojo 知道它会在下面被覆盖。在使用转移符号（transfer sigil）时，你也可以看到这种行为：

```mojo
def consume(var arg: String):
    pass

def use(arg: Balloons):
    print(arg.count, arg.color, "balloons.")

def consume_and_use():
    var balloons = Balloons("blue", 8)
    consume(balloons.color^)
    # String(take=) runs here, which invalidates balloons.color
    # Now balloons is only partially initialized

    # use(balloons)  # This fails because balloons.color is uninitialized

    balloons.color = String("orange")  # All together now
    use(balloons)  # This is ok
    # balloons.__deinit__() runs here (and only if the object is whole)
```

请注意，代码将 `color` 字段的所有权转移给了 `consume()`。在此之后的一段时间内，`color` 字段处于未初始化状态。然后 `color` 在被传递给 `use()` 函数之前被重新初始化。如果你尝试在 `color` 被重新初始化之前调用 `use()`，Mojo 会以未初始化字段错误拒绝该代码。

此外，如果你没有在 `balloons` 生命周期结束之前重新初始化 `color`，编译器会报错，因为它无法销毁一个部分初始化的对象。

Mojo 在这里的策略强大且有意保持简洁：字段可以被暂时转移，但"整个对象"必须使用聚合类型的初始化器构造，并使用聚合反初始化器销毁。这意味着不可能仅通过初始化其字段来创建一个对象，同样也不可能仅通过销毁其字段来销毁一个对象。

### 移动和销毁期间的字段生命周期

消耗移动初始化器和反初始化器都使用 `deinit` 参数约定接收其操作数。这授予对该值的独占所有权，并在函数结束时将其标记为已销毁。在函数体内部，Mojo 的 ASAP 策略仍然适用于字段：每个字段在其最后一次使用之后立即被销毁。

要了解更多关于 `deinit` 约定的信息，请参阅[实例初始化](/docs/manual/lifecycle/initialization/)。

## 显式生命周期扩展

大多数时候，Mojo 的 ASAP 销毁"就能正常工作"。极少情况下，你可能需要显式标记一个值的最后一次使用，以控制其反初始化器何时运行。可以将其视为给生命周期检查器的显式最后使用标记，而不是一种通用模式。

你可能会在以下情况下这样做：

- 在编写有意创建原本未使用的值的测试时（以避免警告或死代码消除）。

- 在编写不安全/高级代码时（例如，操作值的[来源](/docs/manual/values/lifetimes/)的代码）。

- 当你需要相对于特定副作用（例如日志记录或性能分析）确定反初始化器的执行时机时。

通过将该值赋给 `_` 丢弃模式来标记最后一次使用，赋值的位置就是可以销毁它的位置。这会在该行设置最后一次使用，因此反初始化器会在该语句之后立即运行：

```mojo
# Without explicit extension: s is last used in the print() call, so it is
# destroyed immediately afterwards.
var s = "abc"
print(s)  # s.__deinit__() runs after this line

# With explicit extension: push last-use to the discard line.
var t = "xyz"
print(t)

# ... some time later
_ = t  # t.__deinit__() runs after this line
```

:::note
早期版本的 Mojo 在丢弃仅可移动类型时需要使用转移符号（`^`）。这已不再需要，因为编译器实际上并不会移动被丢弃的值。有关转移符号的更多信息，请参阅关于[所有权转移](/docs/manual/values/ownership/#transfer-arguments-var-and-)的部分。
:::
