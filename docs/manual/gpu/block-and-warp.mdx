当多个 GPU 线程在没有定义执行顺序的情况下写入同一内存位置时，就会发生*竞态条件*。计算的最终结果变得不确定，取决于 GPU 硬件对线程的调度和执行时序。这类 bug 以难以调试而闻名，因为它们可能不会在每次运行中一致地出现。

要编写正确且健壮的并行程序，你需要显式的机制来协调线程的执行并管理其内存操作的可见性。这些机制被称为*同步原语*。它们不仅仅是性能优化，而是确保正确性的必要工具。没有它们，线程将完全隔离运行，无法安全地共享中间结果、分配复杂任务或执行高性能 GPU 算法标志性的集体计算。

*屏障*是一种基本的同步原语，它在程序中创建一个汇合点，所有参与的线程必须在此相互等待。当一个线程到达屏障时，它会暂停执行，直到组中的所有其他线程也到达。这确保了所有线程一起通过屏障，保持一致的状态并防止访问共享数据时的竞态条件。

Mojo 提供了两类互补的 GPU 协调工具。*同步原语*（如 `barrier()` 和 `syncwarp()`）协调线程执行并强制内存可见性，但它们本身不执行计算——它们是纯粹的协调机制。相比之下，*集合操作*（如归约、广播和前缀和）将同步与常见计算模式结合：它们既协调线程*又*计算结果。当你需要显式控制线程何时协调时（例如在算法的不同阶段之间管理对共享内存的访问），使用同步原语；当你需要在线程之间聚合或分发数据时（例如计算线程块或线程束中的总和或最大值），使用集合操作。这两种工具对于编写正确且高效的 GPU 代码都是必不可少的，理解何时使用每种工具是构建健壮并行算法的关键。

本指南涵盖 Mojo 用于管理线程块和线程束级别协调的低级原语。有关基础 GPU 架构概念和 GPU 执行模型的详细说明，请参阅 [GPU 简介](/docs/manual/gpu/architecture/)。有关基本内核创建和设备管理的讨论，请参阅 [GPU 编程基础](/docs/manual/gpu/fundamentals/)。本章后面的分块矩阵乘法示例使用 [`TileTensor`](/docs/layout/tile_tensor/TileTensor/) 和 [`stack_allocation()`](/docs/layout/tile_tensor/stack_allocation/) 来分配共享内存块。有关 `TileTensor` 本身的介绍——包括如何在全局、共享或本地内存中创建它——请参阅[使用 `TileTensor`](/docs/manual/tile-tensor/tensors/#creating-a-tiletensor-in-shared-or-local-memory)。

我们将探索 Mojo 的同步和集合通信原语，用于协调 GPU 上的并行工作。关键主题包括：

- [线程块级同步和操作](#block-level-synchronization-and-operations)：如何使用 [`barrier()`](/docs/std/gpu/sync/sync/barrier/) 和 [`gpu.primitives.block`](/docs/std/gpu/primitives/block/) 模块中的线程块归约操作来协调线程块内的所有线程。

## 线程块级同步和操作

本节涵盖线程块内所有线程的协调机制：

- [`barrier()` 原语](#the-barrier-primitive)：基本的同步原语，确保所有线程在继续执行之前到达同一点。
- [线程块级归约操作](#block-level-reduction-operations)：更高级的集合操作（`sum`、`max`、`min`、`broadcast`、`prefix_sum`），将同步与计算结合。
- [线程块同步示例](#block-synchronization-example-tiled-matrix-multiplication)：一个完整的分块矩阵乘法示例，演示屏障的实际使用。

这些工具服务于不同但互补的目的：`barrier()` 是用于协调执行和内存可见性的纯同步原语，而线程块归约操作是内部自行处理同步的集合计算。你可以使用 `barrier()` 构建自定义协调模式，或者在需要同时进行协调和计算时使用线程块归约操作。

### `barrier()` 原语

[`gpu.sync.barrier()`](/docs/std/gpu/sync/sync/barrier/) 函数是协调单个线程块内所有线程的主要机制。它在内核的执行流中创建一个同步点，任何线程都不能通过该点，直到其块中的所有其他线程也到达该点。

`barrier()` 原语做两件事：它既充当执行屏障，又充当内存栅栏。

- 执行屏障：作为执行屏障，`barrier()` 确保块中所有线程的执行在程序中的该点暂停。硬件调度器不允许任何线程继续通过屏障，直到该块中的所有线程都已发出到达信号。

- 内存栅栏：作为内存栅栏，`barrier()` 对内存操作强制执行严格的顺序。它保证任何线程在屏障*之前*执行的对共享内存（以及相对于同一块中其他线程的全局内存）的所有写入操作都已完成，并在所有其他线程通过屏障*之后*对块中的所有其他线程可见。这个保证正是防止线程通过共享内存通信时发生竞态条件的关键。

`barrier()` 最常见的用例是管理对线程块内所有线程共享的快速片上共享内存的访问。以下是典型算法的工作方式：

1. 块中的线程协作将一段数据从高延迟的全局内存加载到共享内存数组中。每个线程负责加载一个或多个元素。

2. 调用 `barrier()`。这对于确保在任何线程尝试使用数据之前，整个数据段已完全加载到共享内存中至关重要。

3. 线程执行计算，对共享内存数组进行读写。此阶段利用共享内存的低延迟来加速算法。

4. 如果计算本身涉及多阶段共享内存通信，可能需要另一次 `barrier()` 调用，以确保一个阶段的结果在下一个阶段开始之前可见。

5. 最后，线程将其结果从共享内存写回全局内存。

:::caution[注意]

`barrier()` 必须被块内的所有线程遇到，以避免死锁。将 `barrier()` 放在条件语句（如 `if` 或 `else` 块）中是常见的 bug 来源。如果条件导致某些线程执行 `barrier()` 而其他线程跳过它，到达屏障的线程将无限期地等待其他线程到达，导致内核挂起。因此，只有在保证块中的所有线程将相同地评估条件并遵循相同的执行路径时，才应在条件代码中使用 `barrier()`。

:::

Mojo 的 `barrier()` 函数在功能上等同于 NVIDIA CUDA 和 AMD HIP 中的 `__syncthreads()` 内建函数，以及 Apple Metal 中的 `threadgroup_barrier(mem_flags::mem_threadgroup)`，为这一基本操作提供了可移植的语法。

:::tip

有关单个线程束内的细粒度同步，请参阅 [`syncwarp()`](#warp-level-synchronization)，它为在同一线程束中一起执行的线程提供了更快的协调，无需块级同步。

:::

### 线程块级归约操作

除了基本的 `barrier()` 原语外，Mojo 还通过 [`gpu.primitives.block`](/docs/std/gpu/primitives/block/) 模块提供更高级的块级集合操作。这些操作将 `barrier()` 的协调功能与常见计算模式相结合，提供了便利性和性能优势。

`gpu.primitives.block` 模块包含几个归约原语：

- [`sum(val)`](/docs/std/gpu/primitives/block/sum/)：计算块中所有线程的 `val` 之和。
- [`max(val)`](/docs/std/gpu/primitives/block/max/)：计算块中所有线程的 `val` 的最大值。
- [`min(val)`](/docs/std/gpu/primitives/block/min/)：计算块中所有线程的 `val` 的最小值。
- [`broadcast(val, src_thread=0)`](/docs/std/gpu/primitives/block/broadcast/)：将 `src_thread` 的值广播到块中的所有其他线程。
- [`prefix_sum[exclusive=False](val)`](/docs/std/gpu/primitives/block/prefix_sum/)：计算块中线程的包含（默认）或排他前缀和（扫描）。前缀和将输入序列转换为累积和：给定 $[x_0, x_1, x_2, x_3]$，*包含*扫描产生 $[x_0, x_0+x_1, x_0+x_1+x_2, x_0+x_1+x_2+x_3]$，其中每个线程接收包括自身在内的所有值的和，而*排他*扫描产生 $[0, x_0, x_0+x_1, x_0+x_1+x_2]$，其中每个线程接收其*之前*所有值的和。

这些操作在内部自动处理必要的同步和共享内存管理，使它们比使用 `barrier()` 和共享内存操作手动实现等效功能更容易正确使用，且通常更高效。

:::tip[提示]

当你需要聚合线程块中所有线程的数据（可能跨越多个线程束）时，使用 `gpu.primitives.block` 操作。当你只需要在单个线程束内聚合时，使用 `gpu.primitives.warp` 操作（如[线程束级归约操作](#warp-level-reduction-operations)中所述），因为它们明显更快。对于归约大型数据集的算法，使用混合方法：首先使用 `gpu.primitives.warp` 原语在线程束内归约，然后使用 `gpu.primitives.block` 操作合并线程束结果。

:::

### 实践中使用线程块操作

线程块级操作通常用于线程必须通过共享内存协调的多阶段算法。典型模式包括：

1. 加载阶段：线程协作将数据加载到共享内存
2. 同步：使用 `barrier()` 确保所有数据已加载
3. 计算阶段：使用共享内存处理数据
4. 归约阶段：使用线程块归约操作聚合结果

这种模式出现在分块矩阵乘法、模板操作和并行归约等算法中，其中共享内存和正确同步的结合比朴素方法带来了显著的性能提升。

### 线程块同步示例：分块矩阵乘法

矩阵乘法受益于一种称为*分块*的技术，我们将大矩阵分解为适合 GPU 快速共享内存的小块。线程块中的线程协作将一个块加载到共享内存中一次，然后所有线程可以多次访问它，而不是重复从慢速全局内存读取。这创建了一个经典的*生产者-消费者*模式：线程协作加载数据（生产者阶段），然后所有线程使用该数据计算结果（消费者阶段）。如果这些阶段之间没有适当的同步，算法会产生不正确的结果。要更深入地理解分块策略，请参阅[我们关于在 NVIDIA Blackwell 上优化矩阵乘法的博客文章中的这一部分](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-2-using-hardware-features-to-optimize-matmul#shared-memory)。

```mojo title="tiled_matmul.mojo"
from std.math import ceildiv
from std.sys import exit, has_accelerator

from std.gpu.sync import barrier
from std.gpu.host import DeviceContext
from std.gpu import thread_idx, block_idx
from std.gpu.memory import AddressSpace

from layout import TileTensor, stack_allocation
from layout.tile_layout import row_major

comptime float_dtype = DType.float32

comptime MATRIX_SIZE = 64
comptime MATRIX_M = MATRIX_SIZE
comptime MATRIX_N = MATRIX_SIZE
comptime MATRIX_K = MATRIX_SIZE

comptime TILE_SIZE = 16
comptime TILE_M = TILE_SIZE
comptime TILE_N = TILE_SIZE
comptime TILE_K = TILE_SIZE

comptime NUM_TILES_PER_SIDE = MATRIX_SIZE // TILE_SIZE
comptime THREADS_PER_TILE = TILE_SIZE * TILE_SIZE
comptime TOTAL_TILES_TO_PROCESS = NUM_TILES_PER_SIDE

comptime matrix_a_layout = row_major[MATRIX_M, MATRIX_K]()
comptime matrix_b_layout = row_major[MATRIX_K, MATRIX_N]()
comptime matrix_c_layout = row_major[MATRIX_M, MATRIX_N]()

comptime tile_a_layout = row_major[TILE_M, TILE_K]()
comptime tile_b_layout = row_major[TILE_K, TILE_N]()


def tiled_matmul_kernel(
    matrix_a: TileTensor[float_dtype, type_of(matrix_a_layout), MutAnyOrigin],
    matrix_b: TileTensor[float_dtype, type_of(matrix_b_layout), MutAnyOrigin],
    matrix_c: TileTensor[float_dtype, type_of(matrix_c_layout), MutAnyOrigin],
):
    var thread_x = thread_idx.x
    var thread_y = thread_idx.y
    var block_x = block_idx.x
    var block_y = block_idx.y

    var global_row = block_y * TILE_M + thread_y
    var global_col = block_x * TILE_N + thread_x

    var tile_row_start = block_y * TILE_M
    var tile_col_start = block_x * TILE_N

    var tile_a_shared = stack_allocation[
        float_dtype, address_space=AddressSpace.SHARED
    ](tile_a_layout)

    var tile_b_shared = stack_allocation[
        float_dtype, address_space=AddressSpace.SHARED
    ](tile_b_layout)

    var accumulator: matrix_c.ElementType = 0.0

    comptime for k_tile in range(0, MATRIX_K, TILE_K):
        var a_global_row = tile_row_start + thread_y
        var a_global_col = k_tile + thread_x
        var b_global_row = k_tile + thread_y
        var b_global_col = tile_col_start + thread_x

        var load_a_valid = (a_global_row < MATRIX_M) and (
            a_global_col < MATRIX_K
        )
        var load_b_valid = (b_global_row < MATRIX_K) and (
            b_global_col < MATRIX_N
        )

        if load_a_valid:
            tile_a_shared[thread_y, thread_x] = matrix_a[
                a_global_row, a_global_col
            ]
        else:
            tile_a_shared[thread_y, thread_x] = 0.0

        if load_b_valid:
            tile_b_shared[thread_y, thread_x] = matrix_b[
                b_global_row, b_global_col
            ]
        else:
            tile_b_shared[thread_y, thread_x] = 0.0

        barrier()

        comptime for k in range(TILE_K):
            var a_element = tile_a_shared[thread_y, k]
            var b_element = tile_b_shared[k, thread_x]
            accumulator += a_element * b_element

        barrier()

    if (global_row < MATRIX_M) and (global_col < MATRIX_N):
        matrix_c[global_row, global_col] = accumulator
```

这种分块算法利用 GPU 的内存层次结构来获得更好的性能。共享内存是一种片上缓存，比全局内存快得多，但大小有限——一个典型的块可能只有 48KB 可用。我们将计算分为多个阶段：线程协作将小块从全局内存加载到这个快速共享内存中，对这些块执行计算，然后对下一组块重复此过程。每个线程加载每个块中的一个元素，创建合并的内存访问以最大化带宽。一旦一个块位于共享内存中，块中的所有线程都可以重复访问它，而不会触发昂贵的全局内存读取。

第一个 `barrier()` 调用出现在协作块加载阶段之后。这个同步点至关重要：它确保块中的所有线程在开始从中读取数据以计算结果之前，完成将其元素写入共享内存。没有这个屏障，就会出现经典的先读后写竞态条件。快速的线程可能抢先开始从慢速线程尚未填充的共享内存位置读取，导致从未初始化数据得到不正确的结果。更糟糕的是，这个 bug 是不确定的——有时代码会工作（如果线程碰巧以有利的顺序执行），有时会失败，使调试极其困难。屏障通过建立明确的先发生关系消除了这种不可预测性：所有写入在任何读取开始之前完成。

第二个 `barrier()` 调用出现在计算阶段的末尾，就在循环继续加载下一组块之前。这个屏障解决了相反的问题：它防止写入期间读取竞态。没有它，快速线程可能完成计算并开始将新的块数据加载到共享内存中，而慢速线程仍在读取旧数据进行计算。这会用部分覆盖的值损坏共享内存，再次产生不正确的结果。这种模式是对称的：第一个屏障保护读取者免受看到不完整写入的影响，而第二个屏障保护读取者免受并发覆盖的影响。这两个屏障一起实现了一个安全的生产者-消费者循环：加载 → 屏障 → 计算 → 屏障 → 重复。两个屏障都是绝对必要的——移除任何一个都会破坏算法的正确性。

## 线程束级操作

虽然线程块是共享内存通信的范围，但线程束是执行调度的基本单位。由于线程束内的线程由硬件同时执行，它们之间的通信比需要跨不同线程束协调的通信快得多。Mojo 为这些高速的线程束内操作提供了一套原语，这对许多性能关键的优化模式至关重要。

本节涵盖单个线程束内的高速协调和数据交换：

- [线程束级同步](#warp-level-synchronization)：如何使用 `syncwarp()` 进行线程束内的细粒度同步，以及何时需要它，何时不需要。
- [线程束级数据交换](#warp-level-data-exchange)：使用 shuffle 操作（`shuffle_up`、`shuffle_down`、`shuffle_xor`、`shuffle_idx`、`broadcast`）进行寄存器到寄存器通信。
- [线程束级归约操作](#warp-level-reduction-operations)：仅在线程束内操作的高性能集合操作（`sum`、`max`、`min`、`prefix_sum`）。

### 线程束级同步

[`gpu.sync.syncwarp()`](/docs/std/gpu/sync/sync/syncwarp/) 函数提供了更细粒度的同步屏障，仅对单个线程束内的线程进行操作。

此函数处理*线程分歧*。在某些 GPU 架构上，线程束内的线程可能由于条件分支而遵循不同的执行路径。`syncwarp()` 强制线程束中指定的线程在继续之前在单一点重新汇聚。

:::tip

要协调线程块内跨多个线程束的线程，请使用 [`barrier()`](#the-barrier-primitive)，它会同步块中的所有线程并为共享内存访问提供内存栅栏保证。

:::

`syncwarp()` 函数接受一个可选的 `mask` 参数。这是一个 32 位或 64 位整数（取决于架构的线程束大小），用作位掩码。掩码的第 `i` 位对应线程束中通道 `i` 的线程。如果某位设置为 1，则对应的线程参与同步；如果为 0，则不参与。默认值 -1（所有位设置为 1）同步线程束中的所有线程。

理解 `syncwarp()` 需要了解其平台相关的行为，Mojo 的可移植 API 将其抽象化了：

- 在支持独立线程调度的 NVIDIA GPU（Volta 架构及更新版本）上，线程束内的线程可以真正地分歧。在这种情况下，`syncwarp()` 编译为活动的硬件指令（`bar.warp.sync`），强制参与的线程相互等待。对于依赖线程束同步行为的算法的正确性而言，它是必要的。

- 在 AMD GPU 上，波前（AMD 中与线程束等价的概念）内的线程由硬件保证以锁步方式执行。它们不能以同样的方式分歧。因此，`syncwarp()` 在 AMD 架构上是**空操作**；Mojo 编译器不会为其发出任何指令。

- 在 Apple Silicon GPU 上，这仅提供 SIMD 组（Apple 中与线程束等价的概念）内的执行同步，没有内存栅栏（等同于 Apple Metal 的 `simdgroup_barrier(mem_flags::mem_none)`）。不支持通道掩码，因此 `mask` 参数被忽略，所有活动通道必须到达此点。

这种差异突显了 Mojo 的一个关键优势。你针对单一的可移植 API 编写代码。编译器负责生成正确的、特定于架构的代码。因此，如果算法依赖 `syncwarp()` 在 NVIDIA 硬件上的正确性，它在其他厂商的硬件上仍然会按预期运行。

:::note

[线程束 shuffle 操作](#warp-level-data-exchange)（如 `shuffle_down()`、`shuffle_xor()` 等）和[线程束归约操作](#warp-level-reduction-operations)（如 `max()`、`prefix_sum()`、`sum()` 等）提供**隐式同步**，**不**需要在它们之前调用 `syncwarp()`。在线程束 shuffle 或归约操作之前调用 `syncwarp()` 是冗余且不必要的。

:::

### 线程束级数据交换

Shuffle 操作是高性能线程束级算法的基石。这些原语使线程束内的线程能够直接通过寄存器交换数据，使其成为实现高效并行模式（如归约、模板计算和滑动窗口操作）的关键。

与需要显式同步和内存事务的共享内存通信不同，shuffle 操作利用线程束的同时执行来实现接近零延迟的数据交换。这使它们非常适合：

- 邻居数据访问：在模板操作或卷积中访问相邻线程的元素。
- 树结构归约：实现用于并行归约和前缀操作的蝶形模式。
- 数据广播：将计算值或常量分发到线程束中的所有线程。
- 滑动窗口算法：高效计算运行最大值、最小值或移动平均值。

#### 线程束 shuffle 操作

[`gpu.primitives.warp`](/docs/std/gpu/primitives/warp/) 模块提供五个 shuffle 原语，每个都针对特定的数据移动模式进行了优化：

- [`shuffle_up(value, offset)`](/docs/std/gpu/primitives/warp/shuffle_up/)：每个线程从具有较低通道 ID 的线程（即通道 current_lane - `offset`）接收值。如果结果通道 ID 小于 0，线程接收未定义的值。

除 `broadcast()` 外，所有这些原语都接受一个可选的 `mask` 参数，该参数具有双重目的：

1. **线程参与**：掩码指定哪些线程参与 shuffle 操作。它是一个 32 位或 64 位整数（取决于线程束大小），其中第 `i` 位对应通道 `i`。如果某位设置为 1，则该线程参与；如果为 0，则不参与。

2. **隐式同步**：掩码还为所有参与线程提供自动同步。掩码中设置了位的所有线程将在 shuffle 完成之前被同步，确保即使在分歧控制流之后也能正确交换数据。

默认值 -1（所有位设置为 1）包括线程束中的所有线程。

:::caution[警告]

在分歧代码中使用完整掩码（所有位设置）时，**线程束中的所有线程最终都必须到达 shuffle 指令**，即使某些线程不主动使用结果。如果某些线程走了一条永远不会到达 shuffle 的路径，这些线程将永远不会到达同步点，导致其他线程无限期地等待它们。

:::

这五个原语构成了复杂线程束级算法的基础，并作为更高级集合操作的构建块。

#### 选择正确的 shuffle 原语

虽然每个 shuffle 原语在技术上都可以执行任何数据交换模式，但某些操作自然适合特定的用例。理解这些模式有助于你编写更高效和可读的代码。

- 如果你需要将一个线程的数据与所有其他线程共享，当源是通道 0 时使用 `broadcast()`，对于任何其他通道使用 `shuffle_idx()`。想象分发一个线程计算的循环边界，或共享"领导"线程做出的决策。

- 对于处理邻居数据的算法——如模板操作或卷积——`shuffle_up()` 和 `shuffle_down()` 是最佳选择。它们让你从相邻线程获取值，而无需共享内存的协调开销。滑动窗口平均值变得像将邻居的值加到你自己的值一样简单。

- 在实现树结构算法（如并行归约）时，`shuffle_xor()` 表现出色。其蝶形通信模式自然映射到这些算法交换数据的方式。大多数高性能归约实现使用 `shuffle_xor()`，因为它具有出色的指令调度特性。

以下是每个原语表现出色的一些具体模式。

`shuffle_idx()` 和 `broadcast()` 适用于：

- 分发计算常量或数组边界
- 在线程束中实现投票机制
- 共享指定"领导"线程的结果

`shuffle_up()` 和 `shuffle_down()` 非常适合：

- 需要相邻网格点的模板计算
- 需要相邻值的有限差分方案
- 任何滑动窗口算法（移动平均值、局部极值）

`shuffle_xor()` 擅长：

- 使用蝶形模式的并行归约
- 任何具有 2 的幂通信步长的计算

在优化性能时，对于寄存器大小的数据，优先使用 shuffle 操作而不是共享内存，并记住 `shuffle_xor()` 对于归约模式通常具有最佳的指令调度特性。

### 线程束级归约操作

`gpu.primitives.warp` 模块还提供更高级的函数，用于在线程束中的所有线程之间执行常见的归约计算。这些函数在可能的情况下利用硬件特定的内建函数，在其他架构上回退到基于 shuffle 的归约：

- [`max(value)`](/docs/std/gpu/primitives/warp/max/)：计算线程束中所有线程的 `value` 的最大值。结果广播到所有通道。

- [`min(value)`](/docs/std/gpu/primitives/warp/min/)：计算线程束中所有线程的 `value` 的最小值。结果广播到所有通道。

- [`sum(value)`](/docs/std/gpu/primitives/warp/sum/)：计算线程束中所有线程的 `value` 之和。结果广播到所有通道。

- [`prefix_sum[exclusive=False](value)`](/docs/std/gpu/primitives/warp/prefix_sum/)：计算线程束中线程的包含（默认）或排他前缀和（扫描）。前缀和将输入序列转换为累积和：给定 $[x_0, x_1, x_2, x_3]$，*包含*扫描产生 $[x_0, x_0+x_1, x_0+x_1+x_2, x_0+x_1+x_2+x_3]$，其中每个线程接收包括自身在内的所有值的和，而*排他*扫描产生 $[0, x_0, x_0+x_1, x_0+x_1+x_2]$，其中每个线程接收其*之前*所有值的和。

你会发现这些原语在计算已经紧密协作的线程之间的聚合时最有用。使用 `sum()` 计算小数据段的总计、平均值或累积值。`max()` 和 `min()` 函数适用于查找数据中的极值或实现线程需要共识的投票机制。`prefix_sum()` 对于*扫描*操作特别有价值——在处理数据时计算运行总计或构建累积结果。它对于需要在每一步跟踪"到目前为止处理了多少？"的算法至关重要。这些操作比使用共享内存和 `barrier()` 调用的线程块级归约快得多。

### 实践中使用线程束操作

线程束操作在需要频繁、细粒度数据交换的算法中表现出色。常见模式包括：

- 滑动窗口操作：使用 `shuffle_up()` 和 `shuffle_down()` 访问相邻通道值。

- 蝶形归约：使用 `shuffle_xor()` 实现高效的树状归约模式，最小化 shuffle 步数。

- 广播计算值：使用 `broadcast()` 在整个线程束中共享单个线程的计算结果（如循环边界或指针）。

这些操作在块级同步开销过大的算法中特别有价值，例如在计算密集型内核的内部循环中，或处理自然对齐线程束边界的数据时。

## 高级同步机制

除了基本的 `barrier()` 和 `syncwarp()` 原语外，Mojo 还为专门用例和架构特定优化提供了额外的同步机制。这些高级原语支持对内存排序、异步操作和指令调度进行细粒度控制。然而，这些机制中的大多数仅在特定架构上可用。有关可用性的最新信息，请参阅 Mojo API 参考文档。

目前仅在 NVIDIA GPU 上可用的机制：

- **信号量**
  ([`gpu.sync.semaphore.Semaphore`](/docs/std/gpu/sync/semaphore/Semaphore/)、
  [`gpu.sync.semaphore.NamedBarrierSemaphore`](/docs/std/gpu/sync/semaphore/NamedBarrierSemaphore/))：
  使用共享锁变量的设备级信号量实现，用于 CTA 间同步。提供
  [`fetch()`](/docs/std/gpu/sync/semaphore/Semaphore/#fetch)、
  [`wait()`](/docs/std/gpu/sync/semaphore/Semaphore/#wait)、
  [`release()`](/docs/std/gpu/sync/semaphore/Semaphore/#release) 和
  [`state()`](/docs/std/gpu/sync/semaphore/Semaphore/#state) 方法，用于协调跨线程块工作的状态管理。

- **命名屏障**
  ([`gpu.sync.named_barrier()`](/docs/std/gpu/sync/sync/named_barrier/)、
  [`gpu.sync.named_barrier_arrive()`](/docs/std/gpu/sync/sync/named_barrier_arrive/))：
  使用屏障 ID（0-16）的硬件加速块级屏障，用于分阶段同步模式。适用于 TMA 操作和高性能流水线算法。

- **内存屏障**：一套用于跟踪异步内存操作和协调共享内存中分阶段同步的函数。包括
  [`gpu.sync.mbarrier_init()`](/docs/std/gpu/sync/sync/mbarrier_init/)、
  ([`gpu.sync.mbarrier_arrive()`](/docs/std/gpu/sync/sync/mbarrier_arrive/)、
  [`gpu.sync.mbarrier_arrive_expect_tx_shared()`](/docs/std/gpu/sync/sync/mbarrier_arrive_expect_tx_shared/)、
  [`gpu.sync.mbarrier_arrive_expect_tx_relaxed()`](/docs/std/gpu/sync/sync/mbarrier_arrive_expect_tx_relaxed/)、
  [`gpu.sync.mbarrier_test_wait()`](/docs/std/gpu/sync/sync/mbarrier_test_wait/)
  和
  [`gpu.sync.mbarrier_try_wait_parity_shared()`](/docs/std/gpu/sync/sync/mbarrier_try_wait_parity_shared/))。

- **线程栅栏**
  ([`gpu.intrinsics.threadfence()`](/docs/std/gpu/intrinsics/threadfence/))：
  内存排序栅栏（无执行屏障），确保内存操作在指定范围（块、GPU 级或系统级）内可见。对无锁算法和跨块通信至关重要。

- **异步批量拷贝同步**
  ([`gpu.sync.cp_async_bulk_commit_group()`](/docs/std/gpu/sync/sync/cp_async_bulk_commit_group/)、
  [`gpu.sync.cp_async_bulk_wait_group()`](/docs/std/gpu/sync/sync/cp_async_bulk_wait_group/))：
  用于协调异步批量内存传输组的函数。对于管理具有批量内存操作的流水线阶段至关重要。

目前仅在 AMD GPU 上可用的机制：

- **调度屏障**
  ([`gpu.sync.schedule_barrier()`](/docs/std/gpu/sync/sync/schedule_barrier/)、
  [`gpu.sync.schedule_group_barrier()`](/docs/std/gpu/sync/sync/schedule_group_barrier/))：

- **等待计数**
  ([`gpu.sync.s_waitcnt()`](/docs/std/gpu/sync/sync/s_waitcnt/)、
  [`gpu.sync.s_waitcnt_barrier()`](/docs/std/gpu/sync/sync/s_waitcnt_barrier/))：
  基于计数值（向量内存、导出和 LGKM 计数器）等待未完成内存操作完成的精确同步原语。仅在 **AMD CDNA GPU** 上可用（在较旧的 AMD 架构上不可用）。

## 最佳实践和常见陷阱

现在我们已经介绍了核心同步原语，让我们重点关注如何正确使用它们来编写可靠且可移植的 GPU 代码。理解常见陷阱对于避免难以重现和调试的 bug 至关重要。

本节提供编写正确、可移植和高效 GPU 代码的指导：

- [编写正确的同步代码](#writing-correct-synchronized-code)：避免竞态条件、死锁，以及理解何时使用 `syncwarp()` 与 shuffle 操作自动处理同步。
- [选择正确的同步级别](#choosing-the-right-synchronization-level)：何时使用线程束级操作与线程块级同步。
- [编写可移植的 GPU 代码](#writing-portable-gpu-code)：使用 Mojo 的抽象来编写在 NVIDIA、AMD 和 Apple 硬件上都能工作的代码。

### 编写正确的同步代码

正确性应始终是你的首要任务。以下问题是并行程序中常见的 bug 来源。

#### 理解和避免竞态条件

快速提醒一下，当多个线程在没有定义执行顺序的情况下写入同一内存位置时，就会发生竞态条件，导致不确定的结果。以下是一个简单示例，线程尝试更新共享计数器：

```mojo
# 错误：竞态条件
shared_counter[0] += my_value  # 多个线程修改同一位置
```

这会导致"更新丢失"，因为读-修改-写序列不是原子的。为防止这种情况，你必须使用 `barrier()` 等同步原语来协调访问，或对简单更新使用 [`Atomic`](/docs/std/atomic/atomic/Atomic/) 操作。例如，你可以使用 [`Atomic.fetch_add()`](/docs/std/atomic/atomic/Atomic/#fetch_add) 方法原子地递增计数器：

```mojo
# 正确：原子递增
_ = Atomic.fetch_add(shared_counter[0], my_value)
```

#### 避免使用 `barrier()` 时出现死锁

`barrier()` 必须被块内的所有线程遇到，以避免死锁。将 `barrier()` 放在条件语句中是常见的 bug 来源。如果条件导致某些线程执行 `barrier()` 而其他线程跳过它，到达屏障的线程将无限期地等待其他线程到达，导致内核挂起。

因此，只有在保证块中的所有线程将相同地评估条件并遵循相同的执行路径时，才应在条件代码中使用 `barrier()`。

#### 何时使用 `syncwarp()`

当线程束内分歧控制流后需要协调对共享或全局内存的访问时，需要 `syncwarp()` 原语。然而，在线程束 shuffle 操作或线程束归约操作之前**不**需要它，因为这些操作通过 mask 参数提供自己的隐式同步。

使用 `syncwarp()` 的情况：

- 线程束中的线程分歧后需要在访问共享内存之前同步
- 你需要确保线程束中的所有线程在继续共享内存操作之前已完成其分歧执行路径

**不**要使用 `syncwarp()` 的情况：

- 线程束 shuffle 操作（`shuffle_down()`、`shuffle_xor()` 等）——这些会自动同步
- 线程束归约操作（`warp.sum()`、`warp.max()` 等）——这些也会自动同步

以下是 `syncwarp()` **需要**使用的示例（用于共享内存协调）：

```mojo
if thread_idx.x < 16:
    shared_data[thread_idx.x] = compute_something()
else:
    shared_data[thread_idx.x] = compute_something_else()

# 这里需要 syncwarp()，因为线程在写入共享内存之前发生了分歧
syncwarp()
var result = shared_data[some_index]  # 现在可以安全读取
```

以下是 `syncwarp()` **不**需要的示例（shuffle 操作）：

```mojo
if thread_idx.x < 16:
    value = compute_something()
else:
    value = compute_something_else()

# 不需要 syncwarp() - shuffle_down() 通过其 mask 自动同步
result = warp.shuffle_down(value, 1)
```

#### 处理 shuffle 边界条件

使用 `shuffle_up()` 和 `shuffle_down()` 时，要注意边界情况。如果源通道越界（例如 `current_lane - offset < 0`），线程将接收未定义的值。在实现滑动窗口等模式时，你必须添加逻辑来正确处理这些边界条件。

### 选择正确的同步级别

设计高效 GPU 算法的核心原则是：使用 `barrier()` 和共享内存在线程束之间协调，使用 `gpu.primitives.warp` 原语在线程束内优化。

这种层次化方法反映了 GPU 的架构。线程束内通信非常快，而跨线程束通信则更昂贵。

- 使用 `gpu.primitives.warp` 原语用于：
  - 紧密循环内的高频操作。
  - 相邻线程之间的数据交换（模板、滑动窗口）。
  - 对小的、线程束大小的数据块进行归约或扫描。
  - 任何性能对延迟关键的地方。

- 使用 `barrier()` 和 `gpu.primitives.block` 原语用于：
  - 协调多个线程束之间对共享内存的访问。
  - 实现具有不同加载、计算和存储阶段的多阶段算法。
  - 聚合块内多个线程束的结果。

### 编写可移植的 GPU 代码

Mojo 旨在编写可移植的 GPU 代码，但了解其工作原理是有帮助的。

首先，Mojo 的 GPU 操作具有自动回退机制。例如，`gpu.primitives.warp.max()` 调用会在最新的 NVIDIA 硬件上自动使用专门的 `redux` 指令，但在其他 GPU 上会回退到基于 shuffle 的实现。你在有专用指令的地方获得性能，在其他地方获得正确性。

其次，始终避免硬编码硬件特定的值。最常见的错误是假设线程束大小为 32。使用 [`gpu.WARP_SIZE`](/docs/std/gpu/globals/#warp_size) 常量来确保你的代码在所有厂商的硬件上正确工作。

最后，对于高度优化的内核，你可以使用 `comptime if` 块来编写架构特定的代码路径，同时保持单一源文件。

```mojo
from std.sys import is_amd_gpu, is_apple_gpu, is_nvidia_gpu

def adaptive_algorithm():
    comptime if is_nvidia_gpu():
        nvidia_optimized_path()
    elif is_amd_gpu():
        amd_optimized_path()
    elif is_apple_gpu():
        apple_optimized_path()
    else:
        # 为未来硬件支持提供保守的回退方案
        portable_path()
```

### 调试同步问题

同步 bug 可能很棘手。以下是一些发现它们的策略：

- 隔离问题：使用简单、可预测的数据模式（如每个线程的 ID）在使用真实数据之前验证你的逻辑。将你的并行算法的输出与简单的顺序 CPU 版本进行验证。

- 跟踪执行：添加 `print()` 语句来跟踪中间值，了解数据如何通过线程束级 shuffle 或归约树流动。

  :::note[已知限制]

  在 Apple Silicon GPU 上，GPU 内核内的每个 `print()` 调用目前最多支持一个字符串字面量参数。此限制不适用于 NVIDIA 或 AMD GPU。

  :::

- 暴露调度依赖的 bug：使用不同的线程块大小进行测试。在一种配置中出现但在另一种配置中不出现的 bug 通常指向竞态条件。

- 使用专用工具：对于复杂问题，使用厂商提供的 GPU 调试工具（如 [NVIDIA Compute Sanitizer](https://developer.nvidia.com/compute-sanitizer)），它可以检测竞态条件和内存访问错误。

## 结论和要点

### 原语和模式总结

我们介绍了 Mojo 用于管理 GPU 内核中并发和通信的低级工具包。这些原语是编写正确和高性能并行算法的基本构建块。

- `gpu.sync.barrier()`：跨线程束确保正确性的基本原语。它提供块级同步点，既充当执行屏障又充当内存栅栏，主要用于协调对共享内存的访问。

- `gpu.sync.syncwarp()`：用于管理单个线程束内线程分歧的细粒度原语。在支持独立线程调度的硬件上，它对正确性是必要的。

- `gpu.primitives.block` 操作：将同步与常见计算模式（如归约）结合的高级原语，跨块中的所有线程操作。它们简化了代码，且通常比手动实现更高效。

- `gpu.primitives.warp` 原语：性能的关键工具包。通过在线程束内实现直接的寄存器到寄存器通信，这些原语允许极其快速的集合操作，避免共享内存的较高延迟。

### 核心思维模型

有效使用这些原语源于 GPU 算法设计的层次化方法。你的关键要点应该是：使用 `barrier()` 和共享内存在线程束之间协调，使用 `gpu.primitives.warp` 原语在线程束内优化。

这个原则鼓励你构建算法以最大化线程束内计算和通信（这非常快），并且仅在必要时使用更昂贵的块级同步来合并结果或管理线程束之间的数据依赖。
