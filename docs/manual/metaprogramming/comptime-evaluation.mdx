要理解 Mojo 的元编程，你需要了解 Mojo 如何在编译时运行代码。有几种情况会触发编译时代码执行：

- 将表达式赋值给 `comptime` 值。
- 求值 `comptime` 条件或循环。
- 将表达式赋值给编译时参数。
- 以及一些不太常见的情况，所有这些都通过 `comptime` 关键字来标识。

以下是一些示例：

```mojo
comptime SIZE = 1024 // 32
```

在这里，表达式 `1024 // 32` 调用了 `IntLiteral.__floordiv__()` 方法。由于它出现在 `comptime` 赋值中，该方法必须在编译时运行。

```mojo
comptime for i in range(4):
   print(i)
```

在这里，`range(4)` 函数需要运行，以便为 `comptime for` 语句生成一个迭代器。

```mojo
var array = Array[Int, get_array_size()]()
```

在这个示例中，`get_array_size()` 函数需要在编译时运行，以确定 `length` 参数，而该参数构成了 `array` 类型的一部分。（例如，如果 `get_array_size()` 返回 32，那么 `array` 变量的类型就是 `Array[Int, 32]`。）

当编译器在编译时上下文中遇到函数调用时，编译器会单独运行该函数，就像它是一个独立的小程序一样。这在概念上类似于 C++ 求值 `constexpr` 的方式。（如果想对此过程做更深入的了解，请参阅[编译器如何运行代码](#how-the-compiler-runs-code)。）

虽然大多数代码都可以在编译时运行，但 Mojo 不会运行依赖于执行环境的代码。以下是一些 Mojo 不会在编译时运行的代码示例：

- 文件 I/O。
- 外部函数调用（例如调用外部库）。
- 可以[引发错误](/docs/manual/functions/#raising-and-non-raising-functions)的函数。

此外，编译器无法在 GPU 上运行函数。GPU 代码中的编译时函数实际上是在 CPU 上运行的。

在运行代码时，编译器可以分配内存，也可以实例化那些会分配内存的类型，比如字符串和集合。在一定的限制下，它可以将编译时值传递给运行时代码，这个过程称为*物化*（materialization）。更多信息请参阅关于[物化](/docs/manual/metaprogramming/materialization/)的小节。

## `comptime` 值

为编译时值*命名*是非常常见的需求。`var` 用于定义运行时值，而我们还需要一种方式来定义命名的编译时常量。为此，Mojo 使用了 `comptime` 声明。最简单的情况下，`comptime` 可以用来定义一个常量值：

```mojo
comptime rows = 512
```

`comptime` 值总是在编译时被求值，因此你可以使用 `comptime` 来强制函数在编译时运行。你可以借此根据编译时可用的信息（例如硬件参数）来计算常量值。

```mojo
comptime block_size = _calculate_block_size()
```

类型是 `comptime` 值的另一种常见用途。由于类型本身就是编译时表达式，因此你可以将 `comptime` 值用作参数化类型的简写（类型别名或 "typedef"）：

```mojo
comptime Float16 = SIMD[DType.float16, 1]
comptime UInt8 = SIMD[DType.uint8, 1]

var x: Float16 = 0  # Float16 works like a "typedef"
```

（这些别名以及其他别名实际上定义在 [`simd` 模块](/docs/std/builtin/simd/#comptime-values)中。）

你还可以对 `comptime` 值进行参数化，以表达更复杂的关系。详细信息请参阅[参数化的 `comptime` 值](/docs/manual/parameters/#parameterized-comptime-values)。

### 编译时作用域

与 `var` 变量类似，`comptime` 值遵循作用域规则，你可以在函数中按预期使用局部的 `comptime` 值。与 `var` 变量不同的是，`comptime` 值可以在任何函数之外的模块级别进行定义。

以下构造会创建一个新的编译时作用域：

- 函数。函数体会创建一个新的编译时作用域。
- 编译时流控制。编译时条件的每个分支都会创建自己的作用域。`comptime for` 循环的循环体也会创建自己的作用域。

在一个给定的作用域中，你只能将 `comptime` 值赋给某个标识符一次。

```mojo
comptime VALUE = 10


def scope_me():
    print(VALUE)  # prints 10
    comptime VALUE = 20
    # comptime VALUE = 30  # error: invalid redeclaration of VALUE
    comptime if True:
        comptime VALUE = 40
        print(VALUE)  # prints 40
    print(VALUE)  # prints 20
```

## 编译时流控制

元编程能做的最简单的事情之一，就是使用编译时流控制来对代码进行条件化或重复。一些常见的用途包括：

- 在不产生运行时开销的情况下，对平台相关的代码（CPU 还是 GPU、Linux 还是 macOS）进行条件化。
- 展开循环以消除运行时分支。
- 在参数化代码中处理不同的数据类型。

与运行时流控制构造不同，编译时流控制构造只会在编译时被求值一次，并决定实际被编译的代码。

### 编译时条件

你可以在任何基于有效编译时表达式（即可在编译时被求值的表达式）的 `if` 条件前添加 `comptime` 关键字。这能确保只有 `if` 语句中实际执行的分支会被编译进程序，从而可以减小最终二进制文件的体积。例如：

```mojo
from std.sys import has_accelerator

def main():
    comptime if has_accelerator():
        run_on_gpu()
    else:
        run_on_cpu()
```

在这个示例中，如果没有可用的加速器，`run_on_gpu()` 函数永远不会被调用，甚至不会被编译。

`comptime if` 语句可以像标准的 `if` 语句一样包含 `elif` 和 `else` 分支。

### 编译时循环展开

你可以在 `for` 循环前添加 `comptime` 关键字，创建一个在编译时完全展开的循环。通常你只应在循环体较小且迭代次数较少的情况下使用它。

循环序列必须是一个有效的编译时表达式（即可在编译时被求值的表达式）。例如，如果你使用 `for i in range(LIMIT)`，那么表达式 `range(LIMIT)` 就定义了循环序列。如果 `LIMIT` 是一个参数、`comptime` 值或整数字面量，那么它就是一个有效的编译时表达式。

编译器会用 `LIMIT` 份循环体的副本替换 `for` 循环，从而完全展开循环。归纳变量（induction variable）在每次"迭代"中都会被替换为一个编译时常量值。例如：

```mojo
comptime for i in range(1, 5):
    b[i-1] = a[i] + a[i-1]
```

这实际上会被展开为如下运行时代码：

```mojo
b[0] = a[1] + a[0]
b[1] = a[2] + a[1]
b[2] = a[3] + a[2]
b[3] = a[4] + a[3]
```

与普通的 `for` 循环（每次迭代都会包含一次边界测试）不同，展开后的循环会编译为无分支的机器码。这在 GPU 上尤为重要，可以避免[线程发散](https://max.modular.com/gpu/block-and-warp/#warp-level-synchronization)。

`comptime for` 构造会在编译开始时进行展开，这可能会大幅增加代码体积和编译时间。

## 编译器如何运行代码

求值编译时代码的过程涉及编译器的三个组件：

- 解析器（Parser）。将代码解析为中间表示（IR）并执行类型检查。
- 解释器（Interpreter）。在编译时运行代码。
- 特化器（Elaborator）。用具体的值替换编译时参数，并生成参数化函数和结构体的具体版本。

当解析器将代码转换为 IR 时，它还会用值替换一些非常简单的 `comptime` 表达式，这个过程称为*常量折叠*（constant folding）。例如，编译器可以将表达式 `2 + 3` 常量折叠为 `5`。被标记为 `@always_inline("builtin")` 的标准库函数是可常量折叠的。无法进行常量折叠的编译时表达式会保留下来，并在特化器中被求值。

当特化器在编译时上下文中遇到函数调用时，它会调用解释器来运行该函数。随后解释器会检查被调用的函数是否已经被*特化*（elaborated）为一个具体可执行的函数。如果没有，解释器会把这个函数加入特化器的工作队列，并等待其完成。最后，解释器运行该具体函数——几乎就像它是一个独立的小程序一样——并将返回值传回给特化器，由特化器将其整合到已解析的 IR 中。

在阅读代码时，需要记住一件重要的事：当函数在编译时被解释时，该函数已经被具体化了：编译时条件已被处理，编译时约束和断言也已被测试。这有时*看起来*与"代码按照它在函数中出现的顺序运行"的预期相矛盾。例如，如果你的函数包含一个失败的编译时断言，编译会在解释器进入函数之前就失败，因此函数的任何部分都不会被求值——甚至包括出现在断言*之前*的代码。
