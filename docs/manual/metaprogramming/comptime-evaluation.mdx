要理解 Mojo 的元编程，您需要了解 Mojo 如何在编译时运行代码。有几个事项可以触发编译时代码执行：

- 将表达式赋值给 `comptime` 值。
- 求值 `comptime` 条件或循环。
- 将表达式赋值给编译时参数。
- 以及一些不太常见的情况，所有这些都用 `comptime` 关键字标识。

这里有一些示例：

```mojo
comptime SIZE = 1024 // 32
```

在这里，表达式 `1024 // 32` 调用了 `IntLiteral.__floordiv__()` 方法。由于它出现在 `comptime` 赋值中，该方法必须在编译时运行。

```mojo
comptime for i in range(4):
   print(i)
```

在这里，`range(4)` 函数需要运行以生成 `comptime for` 语句的迭代器。

```mojo
var array = InlineArray[Int, get_array_size()]()
```

在这个示例中，`get_array_size()` 函数需要在编译时运行以确定 `size` 参数，这是 `array` 类型的一部分。（例如，如果 `get_array_size()` 返回 32，则 `array` 变量的类型是 `InlineArray[Int, 32]`。）

当编译器在编译时上下文中遇到函数调用时，编译器会单独运行该函数，就像它是一个小的独立程序一样。这在概念上类似于 C++ 如何求值 `constexpr`。（对于这个过程的更深入了解，请参阅[编译器如何运行代码](#how-the-compiler-runs-code)。）

虽然大多数代码可以在编译时运行，但 Mojo 不会运行依赖于执行环境的代码。以下是一些 Mojo 不会在编译时运行的代码示例：

- 文件 I/O。
- 外部函数调用（例如，到外部库）。
- 可以[引发错误](/docs/manual/functions/#raising-and-non-raising-functions)的函数。

此外，编译器无法在 GPU 上运行函数。GPU 代码中的编译时函数实际上是在 CPU 上运行的。

在运行代码时，编译器可以分配内存和实例化那些分配内存的类型，如字符串和集合。有一些限制，它可以传递编译时值给运行时代码，这个过程称为*实例化*。有关更多信息，请参阅关于[实例化](/docs/manual/metaprogramming/materialization/)的章节。

## `comptime` 值

想要*命名*编译时值是非常常见的。与 `var` 定义运行时值不同，我们需要一种方式来定义命名的编译时常量。为此，Mojo 使用 `comptime` 声明。在最简单的形式中，`comptime` 可以用于定义常量值：

```mojo
comptime rows = 512
```

`comptime` 值总是在编译时求值，因此您可以使用 `comptime` 强制函数在编译时运行。您可以用它根据编译时可用信息（如硬件参数）计算常量值。

```mojo
comptime block_size = _calculate_block_size()
```

类型是 `comptime` 值的另一个常见用例。由于类型是编译时表达式，您可以将 `comptime` 值用作参数化类型的简写（类型别名或 "typedef"）：

```mojo
comptime Float16 = SIMD[DType.float16, 1]
comptime UInt8 = SIMD[DType.uint8, 1]

var x: Float16 = 0  # Float16 就像 "typedef"
```

（这些别名和其他别名实际上是在 [`simd` 模块](/docs/std/builtin/simd/#comptime-values)中定义的。）

您还可以参数化 `comptime` 值以表达更复杂的关系。有关详细信息，请参阅[参数化 `comptime` 值](/docs/manual/parameters/#parameterized-comptime-values)。

### 编译时作用域

与 `var` 变量一样，`comptime` 值遵守作用域，您可以在函数中按预期使用局部 `comptime` 值。与 `var` 变量不同，`comptime` 值可以在函数之外的模块级别定义。

以下构造创建一个新的编译时作用域：

- 函数。函数体创建一个新的编译时作用域。
- 编译时流控制。编译时条件的每个分支创建自己的作用域。`comptime for` 循环的体也创建自己的作用域。

您只能在给定作用域中将 `comptime` 值分配给给定标识符一次。

```mojo
comptime VALUE = 10


def scope_me():
    print(VALUE)  # 打印 10
    comptime VALUE = 20
    # comptime VALUE = 30  # 错误：VALUE 的无效重声明
    comptime if True:
        comptime VALUE = 40
        print(VALUE)  # 打印 40
    print(VALUE)  # 打印 20
```

## 编译时流控制

使用元编程可以做的最简单的事情之一是使用编译时流控制来条件化或重复代码。一些示例用途包括：

- 条件化平台特定代码（CPU 对比 GPU，Linux 对比 macOS）而无需运行时开销。
- 展开循环以消除运行时分支。
- 在泛型代码中处理不同的数据类型。

与运行时流控制构造不同，编译时流控制构造在编译时求值一次，并确定实际编译哪些代码。

### 编译时条件

您可以在任何基于有效编译时表达式（即可在编译时求值的表达式）的 `if` 条件上添加 `comptime` 关键字。这确保只有 `if` 语句的活跃分支被编译到程序中，这可以减少您的最终二进制文件大小。例如：

```mojo
from std.sys import has_accelerator

def main():
    comptime if has_accelerator():
        run_on_gpu()
    else:
        run_on_cpu()
```

在这个示例中，如果没有加速器可用，`run_on_gpu()` 函数永远不会被调用，甚至不会被编译。

`comptime if` 语句可以像标准 `if` 语句一样包含 `elif` 和 `else` 分支。

### 编译时循环展开

您可以在 `for` 循环上添加 `comptime` 关键字以创建一个在编译时完全展开的循环。您通常应该只将此用于循环体小且迭代次数少的循环。

循环序列必须是有效的编译时表达式（即可以在编译时求值的表达式）。例如，如果您使用 `for i in range(LIMIT)`，表达式 `range(LIMIT)` 定义了循环序列。如果 `LIMIT` 是参数、`comptime` 值或整数字面量，这是一个有效的编译时表达式。

编译器通过用 `LIMIT` 个循环体副本替换 `for` 循环来完全展开循环。归纳变量被替换为每个"迭代"的编译时常量值。例如：

```mojo
comptime for i in range(1, 5):
    b[i-1] = a[i] + a[i-1]
```

这实际上展开为以下运行时代码：

```mojo
b[0] = a[1] + a[0]
b[1] = a[2] + a[1]
b[2] = a[3] + a[2]
b[3] = a[4] + a[3]
```

与包含每次迭代的边界测试的正常 `for` 循环不同，此展开的循环编译为无分支机器代码。这在 GPU 上特别重要，以避免[线程分歧](/docs/manual/gpu/block-and-warp/#warp-level-synchronization)。

`comptime for` 构造在编译开始时展开，这会大大扩展代码大小和编译时间。

## 编译器如何运行代码

求值编译时代码的过程涉及编译器的三个组件：

- 解析器。将代码解析为中间表示（IR）并执行类型检查。
- 解释器。在编译时运行代码。
- 详化器。用编译时参数的具体值替换编译时参数，并生成参数化函数和结构体的具体版本。

当解析器将代码转换为 IR 时，它还会用它们的值替换一些非常简单的 `comptime` 表达式，这个过程称为_常量折叠_。例如，编译器可以将表达式 `2 + 3` 常量折叠为 `5`。标记为 `@always_inline("builtin")` 的标准库函数是可常量折叠的。无法常量折叠的编译时表达式会保留下来并在详化器中求值。

当详化器在编译时上下文中遇到函数调用时，它会调用解释器来运行该函数。解释器然后检查被调用的函数是否已经_详化_以生成具体可执行函数。如果没有，解释器将该函数添加到详化器的工作队列中，并等待它完成。最后，解释器运行具体函数——几乎就像它是一个小的独立程序一样——并将返回值传递回详化器，它将其集成到已解析的 IR 中。

在读取代码时，重要的是要记住，当函数在编译时被解释时，函数已经被具体化：编译时条件已经被处理，编译时约束和断言已经被测试。这有时_看起来_与您的代码按其在函数中出现的顺序运行的期望相矛盾。例如，如果您的函数包含一个失败的编译时断言，编译会在解释器进入函数之前失败，因此函数的任何部分都不会被求值——甚至断言_之前_出现的代码。
