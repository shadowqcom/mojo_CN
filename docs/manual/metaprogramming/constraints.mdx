Mojo 的约束系统让你能够表达超越类型系统所能提供的程序保证。本页面说明如何有效地使用这一系统。

约束通过 `where` 关键字定义，表示调用函数或实例化结构体的前置条件：

```mojo
def pow2[n: Int]() -> Int where n >= 0:
    ...
```

这里 `pow2()` 函数要求其 `n` 参数大于或等于 0。表达式 `n >= 0` 被称为*命题*（proposition）。除了非常简单的表达式外，Mojo 不会字面求值这些命题。相反，它对它们进行符号化分析，跟踪当前作用域内已知为真的命题列表。理解这一符号命题系统是有效使用约束的关键。

Mojo 还支持*编译时断言*（compile-time assertion），在编译时测试一个命题——如果断言求值为 false，则编译失败：

```mojo
comptime assert x >= 0, "x must be greater than or equal to 0."
```

## 定义约束

你可以在以下上下文中使用约束：

- 在函数、方法末尾，或在结构体声明的参数中，用以约束可以绑定到一个或多个参数的值。

  `def pow2[n: Int]() -> Int where n >= 0:`

  单个 `where` 子句可以约束多个参数：

  `def subspan[start: Int, end: Int](self) -> Self where end > start:`

  方法可以基于父结构体的参数限制自身的可用性：

  `def sort() where conforms_to(Self.T, Comparable):`

- 在结构体的 trait 实现列表中，用以声明结构体仅在满足特定条件时才符合某 trait。

  `struct MyContainer[T: AnyType](Copyable where conforms_to(T, Copyable)):`

  在定义参数化类型时，你会用到这种形式，称为*条件 trait 实现*（conditional trait conformance）。详情请参阅[条件 trait 实现](/docs/manual/generics/#conditional-trait-conformance)一节。

## 符号命题

约束系统处理的是*符号*（symbolic）命题。

```mojo
def first[size: Int](array: Array[_, size]) -> array.T where size > 0:
  ...
```

这里 `size > 0` 是约束系统所跟踪的命题。

打个比方，当你为参数标注类型时，你是在要求编译器确保调用者只传递该类型。当你为函数标注约束时，你是在要求编译器确保该命题在调用点为真。

但编译器无法在不运行或解释无限量代码的前提下，在每个调用点测试每一个命题，否则会大幅增加编译时间。因此，调用者需要显式地将"知识"（knowledge）引入约束系统。

### 引入知识

编译器按作用域跟踪知识：每个作用域包含一组已知为真的命题，也称为"知识"，嵌套作用域会从外层作用域累积知识。

有四种方式可以将知识引入系统：

- 在结构体声明内部，结构体上声明的所有约束都是已知的，因为结构体类型的具体实例只有在命题为真时才能被创建：

    ```mojo
    struct List[size: Int] where size >= 0:
      # Knowledge base:
      # - `size >= 0`
    ```

- 在函数内部，函数上声明的所有约束都是已知的，因为调用者只有在保证约束成立时才能调用该函数：

    ```mojo
    def create_list[size: Int]() -> List[size] where size >= 0:
      # Knowledge base:
      # - `size >= 0`
    ```

- 在 `comptime if` 内部，`if` 条件是已知的，因为函数体中的代码只有在条件为真时才会被实例化：

    ```mojo
    comptime if size >= 0:
      # Knowledge base:
      # - `size >= 0`

      comptime if size.is_even():
        # Knowledge base:
        # - `size >= 0`
        # - `size.is_even()`
    ```

- 在 `comptime assert` 之后，被断言的条件是已知的，因为如果 `comptime assert` 条件为 false，编译器就不会实例化该函数。因此，它之后的任何代码只有在断言未触发时才会被实例化：

    ```mojo
    comptime assert size >= 0
    # Knowledge base:
    # - `size >= 0`

    comptime assert size.is_even()
    # Knowledge base:
    # - `size >= 0`
    # - `size.is_even()`
    ```

### 用知识满足约束

每当你调用带有约束的函数时，系统会检查调用点已知为真的命题集合，并判断*已知命题集合*是否是被调用方所声明的*所需命题集合*的超集。

约束系统将所有命题视为符号：它既不知道也不关心表达式的含义，也不解释代码。除了少数非常简单的例外（稍后讨论），系统不会替你执行符号数学运算。相反，它将这些命题视为不透明（opaque），只使用你在调用作用域中显式引入的知识。

```mojo
# A function that wants a non-empty list.
def print_first[size: Int](l: Array[Int, size]) where size >= 1:
    ...


# A wrapper that wants a size >= 2 list.
def print_first_two[size: Int](l: Array[Int, size]) where size >= 2:
     # Error: invalid call to 'print_first': lacking evidence to prove
     # correctness
    print_first[size](l)
    # ...
```

Mojo 在检查约束时并不了解所有调用点，而这些表达式可以引用符号化的参数值——例如 `is_prime(x)`，其中 `x` 是未知的。正因如此，Mojo 无法对 `x` 的所有可能取值解释 `is_prime()`，也无法进行逻辑推导。例如，即便 `is_prime(x)` 与 `x > 2` 都为真，它也无法推导出 `is_odd(x)` 必然为真。

## 编译时断言

使用 `comptime assert` 在代码中的特定位置引入一个已知为真的命题：

```mojo
comptime assert x > 0, "x must be greater than 0."
```

消息是可选的。如果条件在编译时求值为 false，则编译失败，编译器会显示该消息（如果未指定，则显示默认消息）。

Mojo 会把被断言的条件加入该断言之后任何代码的"已知为真"命题列表中。

约束与断言扮演着互补的角色：`where` 子句暴露的是调用者必须证明的*要求*（requirement），而 `comptime assert` 是满足这一要求的一种方式。

## 命题的有限求值

总体而言，可以放心地假设约束系统不会直接对命题求值，所有知识都需要显式提供。然而，约束系统确实会在非常常见的情形下应用一*种很有限的*"智能"。这些作为便利特性提供，不应被视为常态。

其目标是提供一致、可预测的体验，以便用户在熟悉系统的过程中能识别出这些模式。

### 简单蕴含

形式为 `A and B` 的已知命题可以单独满足对 `A` 的要求（或单独满足对 `B` 的要求），尽管在符号层面它们并非同一命题。

```mojo
def create_list[T: Copyable, size: Int]() -> List[T] where size >= 0:
    return List[T](capacity = size)

def create_even_list[T: Copyable, size: Int]() -> List[T] where (
    size >= 0 and (size / 2) * 2 == size
):
    # No need to individually prove `size >= 0` — it's part of the
    # `and` above, so the call to `create_list` type-checks.
    return create_list[T, size=size]()

def main():
    var l1 = create_even_list[Int, 4]()
    print(len(l1) % 2)
    # Prints 0, since the list has an even number of elements.

    # var l2 = create_even_list[Int, 5]()  # Won't compile: 5 isn't even.
```

类似地，对于任意 `B`，`A` 蕴含 `A or B`。

### 规范化

有时同一个表达式可以有多种写法。系统内部总是将表达式简化为规范形式，因此表面上并不相同的表达式可能被系统视为相同。

以下示例不言自明（假设 `x: Int`）：

- `x > 0` == `x >= 1`
- `x >= 2` == `not (x < 2)`
- `x + x` == `2 * x`

函数调用有一个特殊情况。当作为命题的一部分调用函数时，系统会把整个函数调用视为不透明。只有两个完全相同的函数调用才被视为相同。

```mojo
def is_even(x: Int) -> Bool:
  return x % 2 == 0

def needs_even[x: Int]() where is_even(x):
  pass

def forward_even_bad[x: Int]() where x % 2 == 0:
  # ERROR: Needs evidence for `is_even(x)`.
  needs_even[x]()

def forward_even_good[x: Int]() where is_even(x):
  # SUCCESS
  needs_even[x]()
```

:::note Builtin functions

标准库中的某些函数可以在 `where` 子句中被求值。这些函数在核心类型（例如 `Int` 数值）上实现简单操作，编译器对此知情。这些函数在参数上下文中被调用时可以内联到调用表达式中。

然而，不查看源代码就无法识别这些内置函数，而且某个给定函数是否为内置函数可能会在不另行通知的情况下发生变化。

如果你需要可透明工作而非不透明工作的谓词，请考虑将其实现为参数化 comptime 值，这种值总是会被内联。

```mojo
comptime is_even[x: Int]: Bool = x % 2 == 0
```

:::

### 上下文无关折叠

这与其说是一个单独类别，不如说是规范化的极端情形，但可能会让人意外。

某些针对常量的原始操作可以被规范化为一个新的常量。例如：

- `1 + 1` == `2`
- `4 % 2` == `0`
- `1 == 1` == `True`

这也会扩展到常量与非常量混合的表达式：

- `1 + x + 1` == `2 + x`

具体而言，这意味着你可以省去为那些仅是对常量做简单操作的命题显式提供知识：

```mojo
def create_my_list() -> List[2]:
  # No need to provide evidence for `2 >= 0`.
  return create_list[2]()
```

## 最佳实践

这里的示例以函数为重点（在编写函数时声明约束，在调用函数时满足约束），但这些技巧同样适用于其他形式的约束，例如结构体参数约束和条件 trait 实现。

### 编写函数

在编写函数时，如何判断 `where` 子句是否适合你？

#### Q1：你的函数是否处理其输入类型的整个域？

如果你能编写出这样的函数——它对所有输入要么返回结果要么抛出错误，那你根本不需要关心约束。像平常一样编写函数即可。

例如，以下函数*不需要*约束，因为它们保证会返回或抛出：

```mojo
def create_list_opt[size: Int]() -> Optional[List[size]]:
  comptime if size < 0:
    return None
  return ...

def create_list_raise[size: Int]() raises -> List[size]:
  comptime if size < 0:
    raise Error("negative size!")
  return ...
```

约束仅适用于你不想在执行时检查异常情形的情况。

- 约束要求类型检查器排除异常情形，使得通过类型检查的程序保证你（作为函数作者）无需在函数体中使用运行时资源处理这些情形。
- 与往常一样，强制静态保证并非免费。你是在用编译时编写证明的工作换取对运行时错误检查逻辑的削减。在没有硬性限制阻止你在运行时进行错误检查的前提下，这取决于你对用户体验的偏好。

#### Q2：这一限制是否是你代码的核心概念？

如果该条件代表你代码中的一个核心概念，那么使用一个专用类型可能比到处撒 `where` 更容易。

示例：

- 需要表示 SIMD 宽度值的 SIMD 库——这些值并非任意整数。
- 需要表示遵循特定格式规则的路径的文件系统库。
- 需要表示必须处于有效范围内的端口号的网络库。

这是一种好的做法，因为约束在构造时被证明一次（构造时），精炼后的值在被解构之前可以不受约束地传递。你的 API 保持简洁：更少的 `where` 子句，更少的重复断言。

然而，新类型并非免费可得，因为它不再能与原始类型自由互操作。请确保语义足够独特以值得为此编写额外代码。例如，编写新类型通常意味着实现与常见运算符相对应的双下划线方法（加法、减法、相等性等），这些方法需保留新类型的语义。

#### Q3：约束是否可被调用者理解和证明？

如果可以，就使用约束。

让该条件成为函数契约的一部分，使调用者必须证明它。

当满足以下情况时，这通常是正确的选择：

- 该条件是用户能够理解的、面向用户的需求。
- 调用者通常已经需要自行处理"坏"情形（例如，他们可能已经有一个基于该条件分支的 `comptime if`）。

示例：

```mojo
def take_prefix[n: Int, len: Int](...) -> ... where 0 <= n <= len:
  ...
```

一个实用的启发式规则：如果用户读到函数签名后能立即理解*当约束失败时自己做错了什么*，那么 `where` 很可能是正确的工具。

如果约束*不*可被用户理解或*不*可被用户证明，则使用 `assert` 或 `abort`。

如果"坏情形"并非用户能够理解的内容，添加 `where` 约束只会引起更多困惑，因为用户无法合理地自行证明它。

- 这通常发生在你的库返回一个带有某些内部约束的值，并期望用户将这些约束传回。例如，某个通信库将设备句柄作为 `Int` 传给用户，而该句柄具有仅在内部已知的属性（例如非负、特殊位）。接受该句柄的库 API 无法指望用户去证明这些。
- 通常有更多类型安全的方式可以实现同样的目的，所以仅在你不关心类型安全时才这么做。例如，更类型安全的做法是为设备句柄引入一个新类型，这样用户就不太可能意外传入另一个 `Int` 或意外修改返回值。

#### 总结

- 当条件是一种应被一次证明并在各处复用的常见精炼时，使用专用类型。
- 当条件是一种用户可理解的前置条件时，使用 `where`。
- 对于库中的内部不一致性（用户对失败无能为力的情况），使用 `comptime assert` 或 `abort`。

### 调用函数

在调用函数时，如何出示你已满足约束的证据？

这正是约束系统主动引导你处理异常情形之处。

<figure>

![](../images/metaprogramming/constraint-propagation.png#light)
![](../images/metaprogramming/constraint-propagation-dark.png#dark)

<figcaption><b>图 2.</b> 使用受约束的 API</figcaption>
</figure>

#### Q1：受约束的参数是否来自父参数列表？

如果你传递的受约束参数来自函数的参数列表，或是所属结构体上的一个参数，那你基本上是在将值从一个参数列表"转发"到另一个参数列表。前往 Q2。

如果不是，那你是函数体内计算出的该值，处于"构造"领域。前往 Q3。

#### Q2：同样的限制是否适用于你的函数？

如果你将一个受约束的参数转发到另一个受约束的 API，这通常是一个提示：应将同样的要求**传播**到你自己的函数上。

例如，将约束传播给你的调用者：

```mojo
def create_list[T: Copyable, size: Int]() -> List[T] where size >= 0:
  return List[T](capacity = size)

# This function is also only meaningful when size >= 0.
# Make that part of the contract too.
def create_list_and_process[T: Copyable, size: Int](value: T) where size >= 0:
  comptime xs = create_list[T, size=size]()
  ...
```

但如果你希望你的函数接受*更宽的*输入域，那么你的任务是使用 `comptime if` 显式处理两种情形。

例如，在调用前通过检查来收窄域：

```mojo
def create_list_and_fill[size: Int]() -> Optional[List[size]]:
  comptime if size >= 0:
    return needs_nonneg[size]()
  else:
    return None
```

#### Q3：你是否知道该参数已经满足此条件？

如果参数并非来自父参数列表，那它一定是在函数体内计算得到的。

判断所需的约束是否**构造时即成立**。

如果成立，则通过 `comptime assert` 向约束系统表明这一点。注意，这相当于你显式承担起了证明的负担。

不要害怕编写这些断言。约束系统的符号本质意味着它是保守的——对你来说显而易见的逻辑推导，对它而言并不总是"显而易见"。添加 `comptime assert` 不是代码异味，而是与约束系统协作时不可或缺的一部分。

例如，给定一个总是有效的计算参数：

```mojo
# The constraint on hi & lo guarantees a valid size.
# Introduce this piece of knowledge explicitly.

  comptime size = hi - lo
  comptime assert size >= 0, "span is guaranteed non-negative"
  return create_list[size]()
```

但如果约束*不*必然成立，则插入一个 `comptime if` 并显式处理两种情形。

例如，一个可能无效的计算参数：

```mojo
# This version does NOT have a constraint on its inputs.
# Branch on the computation to handle both cases.
def create_list_from_span[lo: Int, hi: Int]() -> Optional[List[hi - lo]]:
  comptime size = hi - lo
  comptime if size >= 0:
    return create_list[size]()
  else:
    return None
```

## 总结

- 约束是 API 契约的一部分。
  - `where` 子句是 **API 作者**要求**调用者**证明的前置条件。
- 编译器不会自动为调用者推导证据。
  - 调用者必须显式提供证据，证明该前置条件始终被满足。
- 如果调用者收到"lacking evidence"（缺乏证据）错误，可以：
  1. 添加约束以将该要求推给自己的调用者。
  2. 对条件进行分支（`comptime if`）。
  3. 断言不变量（`comptime assert`）。
